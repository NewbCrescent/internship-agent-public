**Post-submit outcomes.**
`submitAndConfirm` sorts every submit click into one of five outcomes, read deterministically from the page: (a) **confirmed** (a new confirmation phrase, the site's success container, or a new confirmation URL): the run is submitted; (b) **field errors**: at the 30-second deadline the site marks fields invalid that were not invalid before the click (`aria-invalid="true"` controls and shown error elements: Greenhouse's `<id>-error` and `.helper-text--error`, error-classed elements in Ashby's and Lever's field containers; the selectors are generic and unverified live, so a miss only makes the outcome unknown) and still shows the submit control, so nothing was sent: `SubmissionNeedsInput` makes the run `paused-needs-input` with the approval withdrawn and one open pause per field carrying the site's error text ("School: This field is required."), a field the form recognition cannot find (by id, else a unique label) becoming a `site-error-<n>` safeguard; the pipeline lists it under "Held for you", its message names only the field count, and it is eligible for `pnpm pipeline:retry`; (c) **refused or challenged**: a site error instead of a confirmation (`SubmissionRefused`) or a CAPTCHA that appears after the click (`SubmissionChallenged`) fails the run without marking it submitted, the approval kept, and the pipeline lists it under "Held for you", not errors; (d) **unknown**: nothing recognized (`SubmissionUnconfirmed`, with the same two messages as before) fails the run closed and is listed under errors; (e) **verification code requested** (`verification-code`): after the click, new security-code inputs appear (Greenhouse's `#security-input-<n>` boxes, `autocomplete="one-time-code"`, or a field named or labelled for a security or verification code; none before the click) with text about a code sent by email.
On a Greenhouse board the agent polls the candidate's mailbox read-only (`greenhouseSecurityCodeLookup` in `packages/agent/src/greenhouse-security-code.ts`, through the Gmail `VerificationMailbox` the Workday verification uses, every 10 s for up to 3 minutes) for mail from greenhouse-mail.io or greenhouse.io (dot-bounded) whose subject says "security code", received from 30 s before the click on: mail whose subject names the posting's company (`mentionsCompany`) decides first, and after 60 s of polling without it Greenhouse security-code mail naming another organization counts too (the subject names the board's Greenhouse organization, which on a job-wrapping board is the wrapping service, not the posting's company; a wrong code cannot submit anything, since a step still shown after entry fails closed); in either case exactly one distinct 6–8 character token after a "code …:" anchor (in the text or the HTML read as text) is typed in (one character per box), the step's own submit (the first enabled submit, verify, confirm, or continue control after the boxes) is clicked, and the confirmation wait restarts.
None, several, no mailbox (`INTERNSHIP_AGENT_GMAIL_*` unset), an unreadable mailbox, a field that does not take the code (read back after typing), or a non-Greenhouse page hold the run (`SubmissionCodeNotFound`): `paused-needs-input` with the approval withdrawn and a `site-security-code` safeguard pause ("Greenhouse emailed a security code; it was not found …", naming `pnpm pipeline:retry --run <ref> --reopen-unsubmitted --reason "<why>"`, or `pnpm pipeline:retry --run <ref>` for a non-Greenhouse page), listed under "Held for you" and retryable; a step still shown after the code was entered fails closed (`SubmissionUnconfirmed`, verification-code evidence).
The code is never logged, stored, sent to a model, or put in an event, notice, error, or evidence: every text read after it was typed is scrubbed to "[code]" and no screenshot is taken.
Unverified boundary: the step's markup comes from third-party descriptions of Greenhouse's new boards (open-source automation projects), not a capture (the email's sender, subject, and HTML-only structure were checked against a real message on 2026-11-25, headers and structure only); a different real markup falls back to unknown (fail closed).
Only (b) and (e)'s holds are retry-eligible; (c) and (d) keep their approval, so `pnpm pipeline:retry` refuses them (except the `--reopen-unsubmitted` override with evidence, under Retrying held automatic runs), and nothing is ever retried automatically.
