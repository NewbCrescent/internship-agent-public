**Ashby submits.**
Ashby saves each answer to its server as it is set (a text field 500 ms after typing stops or on blur; a choice, date, or file at once) and refuses a submit click while a save is still running: it shows "We're updating your application (e.g. uploading files), please try again when they're finished." and sends nothing, and the notice goes when the save ends (from Ashby's public bundle, read 2026-11-24; Track 27 found that the earlier unconfirmed Ashby submits had not met this notice: their clicks went to the autofill pane's "Upload file" button).
On Ashby (`packages/browser/src/ats/ashby-submit.ts`) `submitAndConfirm` therefore blurs the focused field and waits 2 s before the click, watches the page for that notice, and clicks again (at most three clicks, 1 s after the notice is gone) only when the notice showed, since that click sent nothing; a click that still meets it fails closed (unknown, with the notice in the evidence detail).
Ashby's failure container (`.ashby-application-form-failure-container`) is read during the wait: its reCAPTCHA Enterprise spam-check variant ("Legitimate applications are occasionally flagged by mistake") or the CAPTCHA error toast holds the run as challenged, any other failure is refused, and neither is clicked again.
The invisible reCAPTCHA Enterprise score is not a visible challenge and is never touched.
On Dover a closed application dialog with no errors counts as a confirmation; on Ashby it never does (its form is inline; its only dialogs are the type-ahead list and the cookie banner), only its success container does.
Ashby's submit is also read on the network (`packages/browser/src/ats/ashby-network.ts`, from Ashby's public bundle, read 2026-11-24; Track 22): from before the first click the page adapter records Ashby's `/api/non-user-graphql?op=…` calls (operation names and HTTP statuses), and for the submit mutation (`ApiSubmitSingleApplicationFormAction`, `ApiSubmitMultipleFormsAction`, or the older `ApiSubmitApplicationFormAction`) the token's kind (present, dummy, missing), Ashby's result type, whether it was a clean `FormSubmitSuccess`, Ashby's error codes and messages, the field errors it names, and its application-limit block message, plus every reCAPTCHA token request (`/recaptcha/enterprise/reload`) and its status; bodies are read in memory only for these and never kept.
Ashby's answer decides: `RECAPTCHA_SCORE_BELOW_THRESHOLD` is held as challenged like the visible spam check (never retried, and refused by `--reopen-unsubmitted`), `FormSubmitSuccess` confirms even without a success container, a `FormRender` naming fields pauses those fields with the approval withdrawn, and the block message is refused.
Once a submit request went out after a click, the agent never clicks again, even after a busy notice.
The page adapter also keeps read-only diagnostics from the same watch (`packages/browser/src/ats/ashby-diagnostics.ts`, Track 27): for each submit click whether it was Ashby's submit button and whether `elementFromPoint` at its centre hit it, every request after the first click as method, host and path (no query or body), console errors and warnings and page errors, and the visible error elements, with the page's own typed values, file names, emails, URL queries, and long numbers removed; they listen to Playwright's events only and change no site script, fingerprint, or launch flag.
When the click provably reached Ashby's submit button and Ashby sent no submit request (no submit mutation, no other Ashby GraphQL call than answer saves, no other Ashby POST, nothing dropped), the run is held as a site safeguard (`SubmissionChallenged`, evidence outcome "challenged", challenge "Ashby sent no submit request after the click on its Submit Application button") with "Ashby did not send the application from the agent's browser; submit it yourself at <url>"; like the spam-check hold it is never retried and `--reopen-unsubmitted` refuses it.
