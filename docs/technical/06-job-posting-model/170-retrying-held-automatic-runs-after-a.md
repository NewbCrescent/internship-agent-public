**Retrying held automatic runs after a fix.**
`pnpm pipeline:retry [--profile real|demo] (--run <id or 8-character prefix> ... | --held) [--dry-run] [--start] [--reason "<text>"]` (`packages/agent/scripts/pipeline-retry.ts`, logic in `src/automatic-retry.ts`) re-runs automatic runs a since-fixed bug held, instead of continuing them with their old pauses.
`retryAutomaticRun(database, runId, { reason })` accepts only a run the pipeline started (`runStartedByPipeline` over the job's APPLYING events) whose status is `paused-needs-input`, `awaiting-approval`, or `failed`, on a job still APPLYING with no other run that is not cancelled; it refuses a run with any answered pause, a run with `submissionApprovedAt` set (which also covers every failed submit: refused, challenged, or unconfirmed submits keep their approval and stay refused), and any application with a submitted or submitting run.
A run the site refused with field errors after the submit click (see Post-submit outcomes) is paused with its approval withdrawn, so it is retryable unless one of its pauses was already answered (then continue it with `pnpm run:answer`).
It cancels the run, moves the job from APPLYING back to READY_FOR_REVIEW, and logs "Automatic run retried after a fix: <reason>" (default reason "the bug that held it is fixed.").
The next pass then starts a fresh automatic run under the current code, logged "started automatically", with the company cap, profile lock, target, and fit rules applied as usual; an automatic stop ("needs you") logged before the job's latest retry no longer blocks it, while a stop after the retry does.
`--run` takes one or more references (repeat the flag or list several), `--held` takes every held (paused or awaiting-approval) run on an applying job, and the command prints one line per run, `retried …` or `skipped … (<reason>)`, then a count.
It holds the workspace's pipeline lock (it refuses while a pass holds it, and in manual checklist mode) and notes when auto-apply is off; `--dry-run` prints `would retry …`, writes nothing, and takes no lock.
`--start` (not with `--dry-run`) then runs one pass with no discovery, like `pnpm pipeline:run --skip-discovery`, in the same process while still holding the lock (`runPipelinePass({ lockHeld: true })`, which refuses unless this process holds the lock); it runs no pass when nothing was retried.
The pass opens the visible browser, so on the PC run it as `xvfb-run -a env -u WAYLAND_DISPLAY pnpm pipeline:retry --held --start`.
A failed submit stays refused, except through the explicit override `pnpm pipeline:retry --run <ref> ... --reopen-unsubmitted --reason "<text>" [--dry-run] [--start]` (`reopenUnsubmittedRun`; `--held` and the default reason are not allowed with it): it reopens a `failed` run whose submit was approved (so clicked) only with positive evidence that the site did not complete it (`unsubmittedEvidence`): a timeline event "Email received: <label> from <greenhouse-mail.io or greenhouse.io domain>: \"Security code for your application to <Company>\"" naming the posting's company, logged after the approval and within 24 hours of it (any label: the watcher's Verification code note, or the Recruiter reply note older watchers wrote), or a stored post-submit evidence capture with the `verification-code` outcome, or post-submit evidence that shows the site never took the click (`judgeSubmitCapture` in `src/unsubmitted-evidence.ts`, pure and deterministic): a capture whose detail is Ashby's busy notice (`ASHBY_BUSY_DETAIL`, Track 16), a `challenged` capture whose challenge is "a Cloudflare Turnstile challenge" on Dover (Track 10), or an older `unknown` capture with no detail, judged only from its saved evidence.json text and flags.
Every such capture must be on the run's own application page (query, hash, and trailing slash ignored; Dover's `app.dover.io/apply/job/<uuid>` and its `jobs.dover.com/job/<uuid>` redirect count as one page) on Ashby or Dover, list no invalid fields, carry no error text, other challenge, confirmation phrase (`readConfirmationFromText`), failure or correction text, or Ashby spam-check text, and still show the submit control (a line "Submit Application" on Ashby, "Apply" on Dover); an older capture must also show the filled form (the uploaded resume line above the submit control: the file name followed by "Replace" on Ashby, "Resume: <file>" on Dover), and an older Dover capture a "Verify you are human" marker.
Every capture saved after the approval must pass, so an older confirming or failing capture vetoes a newer clean one, and the refusal names the newest failing capture and its missing signal ("… its post-submit evidence of <time> shows no Turnstile marker …").
Dover's Turnstile draws its text inside a frame the capture cannot read, so older Dover captures without a marker stay refused.
An Ashby capture with a network record (Track 22) is refused when the record shows Ashby's reCAPTCHA rejection (`RECAPTCHA_SCORE_BELOW_THRESHOLD`; a bot check is never retried), Ashby's server accepting the submission, its application-limit block message, or any submit request whose answer does not show that Ashby refused it; one with no submit request, or only submits Ashby answered with field errors, goes on to the checks above.
A record with no submit request at all (the record starts before the first click) proves nothing reached Ashby, so the failure-or-correction text check is skipped for it (Track 31: Ashby's autofill banner "Please review the information we filled in for you below" and acknowledgment boilerplate read as correction text); every other check, including the spam-check text, still applies, and a capture without a record keeps the text check.
It refuses a run with a recognized confirmation, a run never approved, a submitted run, a paused run other than the security-code hold below, a run the candidate started, an application with another open, failed, or submitted run, and one with no such evidence; the fresh absent receipt check (see Submission uncertainty) applies to every evidence kind and is checked after the evidence, so a dry run that ends "a completed receipt check for this attempt is required" means the evidence passed.
It also reopens a run held on Greenhouse's emailed security code (Track 24) with no receipt check: a `paused-needs-input` run with its approval withdrawn, the `site-security-code` safeguard its only open pause, no confirmation and no trusted receipt, a submit approval on the timeline (the newest event since the run began that starts with "Submission approved", which covers `AUTO_SUBMIT_EVENT`), and every capture since that approval a `verification-code` capture, the newest on a Greenhouse board (`isGreenhouseBoardUrl`).
Greenhouse completes nothing until the code is entered, so this shape is the proof, and the receipt check is not needed (`mail:scan --receipt` never checks such a run: it has no possible-submission hold).
Answered pauses do not block it: they are not carried over, and saved facts cover them.
Its refusals name what is missing (another open pause, a different safeguard, a capture that records another outcome or is on another site, no capture since the approval, an approval not withdrawn, no approval logged).
Its evidence text is "it is held on Greenhouse's emailed security code, which was never entered, and its post-submit evidence shows that step".
It cancels the run, moves the job to READY_FOR_REVIEW, logs "Automatic run retried after a fix: reopened as not submitted (<evidence>): <reason>" (so stops before it no longer block), and prints `reopened <run>: cancelled as not submitted (<evidence>); the application is back to ready for review.` then `Reopened N; skipped M.` (`--dry-run`: `would reopen … (<evidence>)`, nothing written, no lock); the next pass starts a fresh automatic run through the normal pipeline (cap, fit, target, and any numeric daily cap; the reopened run's approval no longer uses a daily slot when a numeric cap is configured).
`--run <ref> ... --reopen-unsubmitted --candidate-verdict not-submitted --reason "<the candidate's words>" [--dry-run] [--start]` (`reopenOnCandidateVerdict`, `candidateVerdictBlocker`; Track 66) reopens a possible submission on the candidate's own verdict that it was not submitted, with no site evidence: the candidate decided it on 2026-11-27 for the possible submissions held with no receipt ("1. retry.").
It takes only named runs (never `--held`, never a default reason), and only a pipeline-started `failed`, `paused-needs-input`, or `awaiting-approval` run whose submit was approved, with no confirmation and no trusted receipt, on an applying job whose other runs are all cancelled, that the hold refresh holds as a possible submission.
For each run it first runs a fresh receipt check (`catchUpSubmissionReceipt`, the same read-only mailbox check as `pnpm mail:scan --receipt`), and it does not start when the mailbox is not set up.
A trusted receipt is recorded as `pnpm mail:scan --receipt` records it (the possible-submission hold resolved, the application status unchanged) and the run is not reopened (`receipt found for …`); an ambiguous, truncated, or unavailable check keeps it held (`skipped …`, exit 1 when unavailable).
With no receipt it cancels the run, moves the job to READY_FOR_REVIEW, logs "Reopened on the candidate's verdict that it was not submitted: <reason>" (stops before it no longer block), and releases the possible-submission hold, so the next pass starts a fresh automatic run under every current rule (the target with the paid-only rule, the company cap, the AI fit, the auto-submit policy, and site safeguards); its approval keeps counting toward that day's numeric cap.
`--dry-run` runs the same receipt check without recording it and prints `would reopen …` or `receipt found for … (dry run, nothing recorded)`; automatic passes, `--held`, plain `--run`, and `--reopen-unsubmitted` without the verdict still never retry a possible submission.
Two more explicit modes never retry anything.
`--run <ref> ... --close-unsubmitted --reason "<text>" [--dry-run]` (`closeUnsubmittedBlocker`, `closeUnsubmittedRun`) closes a pipeline-started `failed` run whose submit was never clicked: it needs the approval, no confirmation, no trusted receipt and no receipt check other than `absent`, the job APPLYING with every other run cancelled, the timeline event "Automatic submission failed: No submit control was found." after the approval, and post-submit evidence after the approval, all `unknown`, whose newest capture shows the posting closed ("The job you are looking for is no longer open" or similar).
It cancels the run, moves the job to READY_FOR_REVIEW with the candidate's own "Posting closed" Quick Skip (so no pass starts it and the review queue hides it; `restoreDiscoveredJob` undoes it), logs "Closed as never submitted (<evidence>): <reason>", resolves the possible-submission hold, and prints `closed <run>: cancelled as never submitted (…); the application is skipped as "Posting closed" and will not be retried.` then `Closed N; skipped M.` (`--dry-run`: `would close …`); its approval keeps counting toward that day's numeric cap.
`--run <ref> ... --correct-submitted --reason "<text>" (--dry-run | --confirm)` (`correctSubmittedBlocker`, `correctSubmittedRun`) corrects a SUBMITTED record: without `--confirm` or `--dry-run` it prints `Not run: --correct-submitted changes a SUBMITTED record; add --confirm once the candidate has agreed, or --dry-run to check it.` and exits 1.
It needs a `submitted` run on a SUBMITTED job whose confirmation is exactly "Submitted with confirmation: Modal dialog closed after submit without errors" and whose only move to SUBMITTED is the relabel event naming that closed dialog, an approval, no trusted receipt, no receipt check other than `absent`, no employer outcome, no "Email received" note after the approval, a pipeline-started run with every other run cancelled, and the same never-taken evidence as the reopen (a record with no saved evidence stays as it is).
It sets the run `failed` with its confirmation cleared (approval, answers, decisions, and the row kept), moves the job from SUBMITTED back to APPLYING, and logs "Submitted record corrected: not submitted (<evidence>); it was recorded as submitted only from \"<old confirmation>\": <reason>"; no row or event is deleted (the funnel still counts the job as having entered SUBMITTED).
The next hold refresh holds it as a manager-owned possible submission, so `pnpm mail:scan --receipt <ref>` can check it, and only then can `--reopen-unsubmitted` reopen it.
It prints `corrected <run>: no longer submitted (…); …` then `Corrected N; skipped M.` (`--dry-run`: `would correct …`).
With Workday account automation on (see Workday accounts), `--held` also releases the Workday account holds the account step left as `unexpected` (`releasableWorkdayHolds`, `releaseWorkdayAccountHold`): those stops happen before any run is saved (the account step runs before the walk), so no run is listed for them and the host's hold in the accounts file is what keeps the pipeline away.
Each is cleared (email, password, account state, and creation time kept) with a line `released the Workday account hold on <host> (<reason>): the next pass signs in with the saved password.` (or `tries the account step again.` when no usable password is saved) and a count `Released N Workday account hold(s).`; `--dry-run` prints `would release …` and writes nothing; `--start` runs the pass when a run was retried or a hold released.
CAPTCHA, existing-account, refused-password, wrong-password, lockout, interrupted-creation, and verification holds are never released here; an unreadable accounts file prints `Workday account holds not released: the accounts file cannot be read.` and exits 1.
Without the account settings the output is unchanged.
A job-level hold (a stop logged before any run was saved) is not a held run: `--held` leaves it, and only `--job <ref> --verified-hold` releases it (see **Submission uncertainty and verified retries**).
The local `automatic-retry` suite (`pnpm test:agent:retry`) covers it with fake pages and temporary accounts files, no network.
