**Receipt-confirmed submissions (Track 85).**
A trusted receipt for a run held as a possible submission now marks the application submitted (`recordApplicationReceipt`, `packages/db/src/application-hold-repository.ts`).
In one transaction it records the receipt check, marks the run submitted with `RECEIPT_CONFIRMATION_TEXT` ("Confirmed by the employer's application receipt email (receipt check).") and its decisions' filled, chosen, and checked values as its submitted answers, moves the job to SUBMITTED with "Submitted with confirmation: <that text>", and resolves the possible-submission hold.
It does so only when the hold is active, the run is not submitting, submitted, or cancelled, the job is not SUBMITTED or past it, and no other run of the job is submitted or submitting; the private proof key is never put in the confirmation text.
The receipt rules are unchanged (explicit receipt language, a trusted sender, one matching posting and attempt after the attempt time), so nothing is marked submitted without a trusted receipt or a recognized confirmation, and a possible submission is never retried.
The Gmail watcher records receipts on arrival as before, and every pipeline pass now runs `checkPendingSubmissionReceipts` (`packages/agent/src/submission-receipts.ts`) after its advance step.
That check first applies trusted receipts recorded before Track 85, or while their run was still submitting (`promoteConfirmedReceiptRuns`), then refreshes the holds and checks every open possible-submission hold attempted in the last 14 days in one read-only Gmail session with the single-run bounds (300 UIDs, 100 bodies, 45 s).
It reads headers, then bounded bodies only for messages a trusted sender sent after an attempt, and records nothing when the mailbox is not set up or cannot be read.
The pass log says `Receipts: checked N possible submission(s) for an employer receipt; M marked submitted.`, or that they wait because the Gmail mailbox is not set up or could not be read, or `Receipts: not checked (<code>); the pass is unaffected.` when the check fails.
A receipt the pass confirms joins that pass's submitted list, its `SUBMITTED` log line, `pipeline-status.json`, and the notice's "Sent:" section; one the watcher confirms between passes shows in the digest's "Sent since last update" and on the board as a confirmed submission.
A policy submit the page seemed to confirm on a site whose confirmation page is not captured (`SubmissionUnverified`) is no longer reported as an error: the pass report lists it under `possibleSubmissions`, and its timeline note starts `POSSIBLE_SUBMISSION_NOTE` ("Automatic submission held as a possible submission: ").
Track 80's notes for the same hold ("Automatic submission failed: The auto-submit policy clicked the final submit of …") are read the same way (`isPossibleSubmissionNote`, `packages/domain/src/submission-mode.ts`).
The pass log lists each as `sent, waiting for its receipt <posting>: <reason>`, the pass notice once per run under "Sent, waiting for the receipt email:", the daily digest as `Sent, waiting for the employer's receipt email: N (<companies>)`, and the board as the "waiting for a receipt" blocker (`awaitsReceipt`, `packages/agent/src/application-holds.ts`).
A run at the submit step that `NO_APPLICATION_CONTENT_BLOCKER` holds reads `held, not ready: …` in the digest, never `ready, say "send <company>"`.
The proof is synthetic: an in-memory mailbox, synthetic runs, and fake pages; no live receipt has yet moved a real possible submission to SUBMITTED.
