`pnpm pipeline:watch [--profile real|demo] [--once] [--interval 300]` is the doorbell: for each enabled GitHub list it asks `api.github.com` for the latest commit with the saved ETag (`<workspace data>/list-doorbell.json`; `GITHUB_TOKEN` is sent when set).
A 304 means nothing changed and nothing else runs; a new commit (or a list never seen) runs one pass (`scripts/pipeline-pass.ts`, shared with `pipeline:run`) for just those sources, and the state is saved only after the pass so a crash rings again.
A tick does nothing while another pass holds the pipeline lock.
The pass releases the lock on every path, and the tick and the pass each close the workspace's shared cached database handle with `closeProfileDatabase` (packages/db), which also forgets it, so the next pass or tick in the same process opens a fresh one; the local `pipeline-pass` suite (`pnpm test:agent:pass`) runs ticks and passes against a disposable workspace with injected fetches.
Each pass writes `<workspace data>/pipeline-status.json` (submitted, held with reasons, ruled out, stopped, waiting for sign-in, errors), which `pnpm pipeline:status` prints, and the watcher appends to `<workspace data>/pipeline-logs/<date>.log`.
`pnpm pipeline:schedule install|remove|status` installs the OS timer that runs `pipeline:watch --once` from a login shell: a launchd agent `com.internship-agent.watch.<profile>` on macOS (`StartInterval`, also at login and on wake) or a systemd user timer on Linux (WSL runs it only while WSL is up).
The browser stays visible-mode on Linux too: when `xvfb-run` is installed the service runs each pass on its own Xvfb virtual screen (no desktop display is passed, so a stuck WSLg display cannot hang the launch); otherwise it records the installer's `DISPLAY`/`WAYLAND_DISPLAY`, which a systemd user service does not inherit.
Non-GitHub sources are not watched; `pnpm pipeline:run` still checks them.
