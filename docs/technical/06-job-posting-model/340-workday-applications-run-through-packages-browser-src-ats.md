Workday applications run through `packages/browser/src/ats/workday.ts`.
`createWorkdayPage` reads Workday's `data-automation-id` markers observed on live sites: Apply (`adventureButton`) then Apply Manually (or Continue for a saved draft), the multi-step `applyFlowPage` with its `progressBarActiveStep`, fields in `formField-*` containers (text inputs, listbox buttons whose options are read by opening them, radio groups labelled by their container, single checkboxes, file inputs, search-and-pick prompts, split date parts), the resume upload `file-upload-input-ref`, and the footer's `pageFooterNextButton`.
A radio is chosen by the option label read from the form (its `label[for]` text, else aria-label, else value), so a radio whose accessible name is its question (aria-labelledby) is still found; it is checked, else clicked through its label, and read back; a choice the page does not keep pauses with that reason (Track 32, employer-e.wd5).
Entering (`enterApplication`) waits up to 15 s on the job page for Apply, Workday's closed-posting page (its `errorContainer` saying "The page you are looking for doesn't exist", read twice in a row), or a security check (Workday's Cloudflare page `cloudflare_error`, or a visible challenge `challenge.ts` recognizes; never solved or bypassed), and after Apply Manually up to 20 s for the flow, the account form, or Workday's `cloudflare_error` page (a CAPTCHA on the account form stays the account service's hold).
A closed posting stops the run (`PostingClosed`): an automatic run logs "Automatic browser run found the posting closed: …", gets the candidate's "Posting closed" Quick Skip (the review queue hides it, no pass starts it again, `restoreDiscoveredJob` undoes it), and is reported as ruled out rather than stopped.
A security check stops it as "Automatic browser run needs you: …"; a page with neither the application nor a closed notice stops it as "No Workday application opened at <url>: …".
Each of these entry stops saves `workday-entry` evidence.
A dropdown's list opens in a portal a moment after its button is clicked and the previous list can still be on screen while it closes, so the adapter first closes an open list and waits for it to go (up to 2 s), reads only the list the button names in `aria-controls` (else the open `activeListContainer`, else a visible listbox outside other fields, never a field's picked items), waits up to 5 s until its options stop changing, and picks an option only inside that list (`packages/browser/src/ats/workday-lists.ts`).
Required fields are the labels ending in `*`; values a field already shows become `currentValue` and are kept when nothing better is known.
`walkWorkdayApplication` plans each step (profile, facts, package answers, the candidate's answers to earlier pauses, voice drafts), fills, and clicks Save and Continue; it stops at the first step with open questions (consent questions always pause; sensitive ones pause unless a saved self-identification answer matches exactly one option), on Workday's own validation errors, or at Review.
Workday's errors are read from the page (`readWorkdayErrors`: `errorMessage`, `inputAlert`, the `errorBanner`'s items, and alerts, with the `formField-*` container and label of inline errors) and become one pause per error (`workdayErrorPauses`): "<field label>: <Workday's error text>" on `<step>::workday-error::<field id>` when the error sits on a form field or names exactly one, otherwise `<step>::workday-error-<n>` labelled with the page's label or the step name; banner items repeating an inline error add none, and at most 10 are made.
The single "<step> (Workday errors)" pause remains only for a step that would not save without showing any error text.
An answer to a Workday error pause fills its field on the next walk whatever the planner decided (`applyAnswers` in `packages/agent/src/workday-run.ts`) and is never saved to generic question memory (`isWorkdayErrorPauseId`, reason `workday_error`), because its label carries Workday's text.
Every such stop saves Workday evidence for the run.
Save and Continue stores a draft on the employer's Workday; only a submit with the candidate's recorded approval re-walks to Review and clicks Submit, and a submission counts only when Workday's confirmation appears.
If Workday shows a sign-in form, the site is marked signed out and the pipeline waits for the candidate (with the account opt-in, automatic runs first sign in or create the account, see above).
Real sites (employer-a.wd115 and employer-b.wd3, seen 2026-11-19) draw the apply flow with its "Create Account/Sign In" step before the account form, so entering reads the active step too, and a walk that meets that step or any password field throws `WorkdayAccountWall`: the run signs in (or creates the account) once and walks again, or holds; the account step's Email Address, Password, and Verify New Password are never planned, filled, or paused as questions.
Workday wraps every create-account button in `noCaptchaWrapper` with no challenge inside, and pages may carry the invisible reCAPTCHA badge (an iframe titled "reCAPTCHA"): neither counts.
An account screen is a CAPTCHA only when `challenge.ts` reads a challenge the candidate would see, a visible hCaptcha or Turnstile frame is shown, or Workday's robot text appears.
Pause and decision ids are prefixed with the step name (`My Information::formField-…`).
The first real Workday runs remain supervised: steps behind sign-in have only been exercised against the local fixture.
The readiness wait counts only visible field containers (Workday can draw a step's fields before they can be read), and a step read with no fields is read once more and never saved past: the walk stops as blocked ("could not read any field").
