A stop the pipeline logged before any run was saved ("Automatic browser run needs you: No Workday application opened at …") leaves a job-level hold (`job:<job id>`) that `--run` cannot name and `--held` does not touch.
`pnpm pipeline:retry --job <job ref> --verified-hold --revision <n> --recheck <hex-ref> --reason "<reason>" [--dry-run]` (`requeueVerifiedJobHold`) releases one: only a manager-owned `automation-fault` or `account-stop` job-level hold at the exact current revision whose current observation still matches, on a READY_FOR_REVIEW job with no run that is not cancelled, when no submit was ever attempted (no auto-submit or "Submission approved" note, no "Automatic submission failed" or reopened-as-not-submitted note, no SUBMITTED event, no submit approval, confirmation, or receipt check on any of its runs, no evidence other than the pre-submit account, Workday, and iCIMS stops, no employer outcome), and with a recheck not used before for that hold.
An `account-stop` hold is a Workday or iCIMS account step that waited ("Automatic browser run waiting: Workday|iCIMS <host>: …") after an older stop; the requeue releases only the job, and the host's own account hold stays until it is cleared (`pnpm icims:account --site <host> --clear-hold` for iCIMS), so a still-held host keeps the job waiting without a browser (Track 69).
In one transaction under the pipeline lock it logs "Automatic run retried after a fix: <reason>" on the job (still READY_FOR_REVIEW), records the recheck reference, and resolves the hold; the note ends the stop for `stoppedSinceRetry` and is read as the job's newest hold source, so a later refresh does not reopen the hold.
The next pass may then start the job under its normal fit, cap, target and approval checks.
It is single-target, takes no `--run`, `--held` or `--start`, and refuses in manual checklist mode.
