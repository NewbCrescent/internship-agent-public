Agent-created Workday accounts are opt-in, at the candidate's request: `INTERNSHIP_AGENT_WORKDAY_ACCOUNT_EMAIL` (with `INTERNSHIP_AGENT_AUTO_APPLY=1` and manual checklist mode off; `workdayAccountSettings`) must equal the profile email, or Workday runs wait with a mismatch reason and nothing is typed.
Sessions stay per site, but accounts are kept per Workday host (tenant).
When an automatic run meets a sign-in wall (`packages/agent/src/workday-account-service.ts`, screens read by `packages/browser/src/ats/workday-account.ts`), the agent signs in with that host's saved password, or creates the account: a random 16-character password per host (upper, lower, digit, symbol; never reused) is saved first, as `pending`, in an owner-only accounts file (0600 file, 0700 directory, atomic writes; `INTERNSHIP_AGENT_WORKDAY_ACCOUNTS_FILE`, default `~/.config/internship-agent/<profile>/workday-accounts.json`, required when `INTERNSHIP_AGENT_DATA_DIR` is set; a damaged file is refused and never overwritten), then typed into the create form.
Only the named email, password, and verify-password fields and the terms checkbox are touched (never Workday's robot honeypot); the checked terms label is logged on the job timeline as part of the candidate's request.
The auto-submit path only signs in with a saved password; candidate-started runs never use account automation.
When Workday asks to verify the email, the agent reads the candidate's Gmail over IMAP (TLS 993, `INTERNSHIP_AGENT_GMAIL_ADDRESS` and a Gmail app password in `INTERNSHIP_AGENT_GMAIL_APP_PASSWORD`; `src/gmail-mailbox.ts`, imapflow loaded lazily) in read-only mode: the INBOX is opened with EXAMINE, nothing is marked seen, deleted, moved, or sent, only messages whose From/Subject mention Workday, the tenant, or the company have their bodies read, in memory only, and nothing about them is logged or sent to a model.
It polls about every 10 seconds for about 3 minutes and accepts exactly one https link on the tenant's host or a dot-bounded Workday domain (`*.myworkday.com`, `*.workday.com`) whose path names an activation step, opens it in a new tab of the run's browser context, and signs in.
Typed email codes are not supported and hold.
After the create-account submit the agent waits up to 60 seconds for Workday's answer, checking the page every 500 ms (a sign-in submit waits 20 seconds; tests inject the wait's clock and length through `WorkdayAccountRuntime.accountWait`).
The submit click goes to the one click filter Workday draws over the form's own submit button (`signInSubmitButton`, `createAccountSubmitButton`; the real button is hidden under it) inside its `noCaptchaWrapper`, whatever the filter's label, since Workday labels it by its internal view (a sign-in filter reads "Submit" on rockwellautomation.wd1); else a filter with the button's label beside that button, then inside the sign-in content or a dialog, never the first such filter page-wide, since "Sign In" also names the header's utility button and the "Already have an account?" link.
The agent clicks the selected visible control once and reports a click failure if the control cannot be activated.
That click comes no sooner than 1 second after the agent first sees the form (its own submit button, or the click filter over it, visible), measured from that moment so typing time counts: Workday's sign-in widget silently drops an account submit made under 500 ms after the button mounts, and the candidate chose on 2026-11-24 to let the agent wait about a second (AGENTS.md's only site-safeguard allowance); the wait is real time even when tests inject the answer wait's clock.
It recognizes: signed in (the application shows), the account created (the sign-in form, or Workday's email-method chooser, with no error: on tenants that verify emails Workday's create handler sends the page to the career site's `/login`, which on nvidia.wd5 shows only Sign in with Google, LinkedIn, or email; read-only capture and Workday's public bundle, 2026-11-25), a "verify your email" screen (the Gmail flow above), a not-verified account message ("Your account has not been verified", "verify your email", "resend the verification email"), even one that also mentions the password, and the same notice drawn as plain text while the form stays up (new since the submit), "account already exists", an error the agent does not recognize (shown three checks in a row, including Workday's `errorBanner` items), and a CAPTCHA.
Workday's generic sign-in failure ("You may have entered the wrong email address or password or your account might be locked.", and any sentence that hedges a lock with may, might or could while naming wrong credentials) is a refused sign-in, not a lockout; only unambiguous text ("Your account has been locked", "too many failed (sign-in) attempts", "temporarily disabled") is a lockout.
"Already exists", and no answer within 60 seconds, lead to one sign-in with the password just saved, since the account may exist with it: signed in goes on with a timeline event, a verification screen goes to the Gmail flow, and a refused sign-in holds as `exists` (account refused; "signing in once with the saved password did not work") or, after no answer, as `interrupted` ("so the account was probably not created"); the create form is never submitted twice.
A refused sign-in with a saved `pending` password (an account an earlier run started to create but never confirmed, as when Workday dropped the submit, or one created on a tenant that verifies emails) first, with a mailbox, makes one mailbox read anchored to that account's creation time under the tenant-origin rule below ("…the agent looks for that account's verification email first."): a link found there is opened, the account is saved as created (opening any verification link saves a `pending` account as created), and the host holds as `verify-email` for a later pass with no create submit.
Otherwise, or without a mailbox, the agent submits the create form once with that saved password on an automatic run, and does not sign in again in that call: signed in goes on; a create that shows the sign-in form saves the account as created and holds as `verify-email` ("the agent signs in on a later pass", retried after an hour); a verification request runs the Gmail flow, which after opening the link holds the same way instead of signing in; "already exists" holds as `exists` (account refused), no answer as `interrupted`, and a refused password, a CAPTCHA, or an error as after a first create.
On the auto-submit path (sign-in only) a refused pending password still holds as `interrupted`.
If the create form's Sign In link opens the email-method chooser on the expected host, the agent selects email once before continuing to the sign-in form.
Create timeouts retain the adapter's observed same-host request or response status and page transition in the follow-up event or hold.
When both the create and its first sign-in time out, the agent makes one mailbox read anchored to the pending account's creation time if a mailbox is configured.
It opens a link only when the existing matching rules find exactly one and its HTTPS origin matches the tenant's host.
Missing, ambiguous, unreadable, and other-host results preserve the existing unexpected hold and pending account state.
The agent reports activation navigation failure without the link or token.
When the create shows the sign-in form or the chooser and the sign-in that follows gets no answer within 20 seconds, Workday may be ignoring sign-ins until the email is verified, so with a mailbox the agent logs "Workday did not answer the sign-in after the account was created; the agent looks for the verification email." and runs the Gmail flow (no email holds as `verify-email`, retried after an hour); this applies only right after this run created the account.
A refused sign-in there (Workday's generic failure, which nvidia.wd5 gives an account whose email is not yet verified) logs "Workday refused the sign-in right after the account was created; the agent looks for the verification email." and runs the Gmail flow too (without a mailbox it holds as `verify-email`); so does a refused sign-in on a pass that retries a `verify-email` hold ("Workday refused the sign-in while the account waits for email verification; …").
A sign-in refused again after the link was opened holds as a refused password.
An unrecognized error holds as `unexpected` with Workday's own text, redacted of the email and password, in the reason ("Workday showed an error after the create-account submit: "…"").
Every hold reason names what happened.
Anything else holds the host (`WorkdayAccountHeld`; the pipeline reports it under `waiting` with reason `workday-account` and a detail, logs "Automatic browser run waiting: …", and saves no run): a CAPTCHA (never solved or bypassed), an existing account or a refused password (never reset or retried with another password), a wrong saved password, a lockout, a text-message or app method, or an unknown screen.
The hold is stored with the host's entry and mirrored to the site's session detail on the Workday accounts page.
Only a missing or unreadable verification email is retried automatically, after 1 hour, doubling per attempt up to 24 hours; `pnpm pipeline:retry --held` releases `unexpected` holds (see Retrying held automatic runs); other holds wait until the candidate signs in with Open sign-in; `pnpm workday:account --site <host> --clear-hold` releases any one host's hold.
Every account-step hold saves Workday evidence for the job (see Post-submit evidence).
`pnpm workday:account [--profile real|demo]` lists hosts and their state; `--site <host or URL>` prints that host's email and password; `--site <host> --clear-hold` clears that host's hold instead (email, password, and account state kept; nothing secret printed) so the next pass retries it, for a hold known to be wrong; `--check-mail` checks the Gmail connection.
The status file of a pass does not yet carry the hold detail.
