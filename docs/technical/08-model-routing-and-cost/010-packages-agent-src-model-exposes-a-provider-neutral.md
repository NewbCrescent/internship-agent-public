`packages/agent/src/model/` exposes a provider-neutral `complete(task, { tier })` interface.
Domain packages never name a model.
`packages/jobs` accepts a `RequirementClassifier` by injection — the same pattern as `GitHubClient` and `SemanticQuestionMapper` — and the orchestrator in `packages/agent` is the only place that chooses between the deterministic and model-backed implementation.
With no `MODEL_API_KEY` configured, ingestion runs fully deterministically rather than failing; those rule labels never drive an automatic run, because the pipeline starts a browser run (and so auto-submit) only when every requirement row has `extraction = 'MODEL'`.
With a model configured there is no rule-label fallback: `ModelRequirementClassifier` returns a model decision for every requirement line or throws `RequirementLabelsUnavailableError`, and a model answer that leaves a line unlabelled is treated the same way.
It sends `reasoning_effort: "medium"` (reasoning tokens count against `max_tokens`), labels batches of 10 lines two at a time (budget 2,000 + 600 per line), splits a batch in half on a budget overrun, an unparseable or incomplete answer, or a timeout (each half keeps at least the parent's budget), retries a single line at doubled budgets up to 12,000 (at most twice), and stops after 48 calls per posting.
A posting the model still cannot label is stored (snapshot, locations, pay, technologies, constraints) with no requirement rows and a `requirement_label_holds` row (migration 0027) holding the reason, plus an application event; while held it is not analyzed, prepared, or run.
Each pipeline pass first retries up to 25 held postings from their stored snapshots (`src/requirement-relabel.ts`; dismissed postings are skipped), replacing the requirements and clearing the hold in one transaction and re-evaluating an existing match; each posting still held adds "AI requirement labels unavailable; will retry: <Company> — <Title>." to the pass errors.
The dashboard's Analyze button retries that posting's labels first.
`defaultedEnrollmentStatement` (graduate-only exclusion on defaulted PREFERRED lines) applies to rule labels only; the classifier prompt instead tells the model that a bullet stating who the role is for (current enrollment in a named degree program or level of study) is HARD unless framed as preferred.
Before this change a failed classification silently kept rule labels stamped `MODEL`; `pnpm labels:hold-fallback [--profile real|demo] [--apply]` finds postings with stored rule labels or a failed classification call before their current snapshot and, with `--apply`, holds the repairable ones (DISCOVERED, ANALYZING, NOT_QUALIFIED, QUALIFIED) under the pipeline lock: no deletes, no status changes, no model calls; the next pass relabels them.
Every model call in a process goes through one shared `ModelRateLimiter` per endpoint and model (`src/model/rate-limiter.ts`), set from `MODEL_REQUESTS_PER_MINUTE` and `MODEL_TOKENS_PER_MINUTE` (defaults 100 and 3,000,000, the configured contributor model's published limits).
It admits calls at 90% of both limits, spaces starts evenly (about one every 0.67 s at 100 RPM) rather than bursting, and reserves each call's estimated input plus its full `max_tokens` against the token budget, settling to the provider's reported usage afterwards.
A 429 or 503 pauses the whole limiter for `Retry-After` (or 2, 4, 8, 16 s); a network error ("fetch failed") and a 500 or 502 back off the same way without pausing the limiter; each is retried up to five attempts in total.
A 504 and the provider's own two-minute timeout are not retried by the provider (the same request would likely time out again), and the request timeout covers the request, never the wait for a slot.
A truncated (`finish_reason: "length"`), empty, unparseable, or wrongly shaped answer raises a typed error (`ModelOutputBudgetError`, `ModelInvalidOutputError`, `ModelTimeoutError` in `src/model/provider.ts`) so callers can send less work per request.
Separate processes (the dashboard and `pnpm pipeline:run`) each hold their own limiter, which the 10% margin and 429 handling absorb.
Discovery ingests up to `INTERNSHIP_AGENT_MODEL_CONCURRENCY` postings at once (default 32, 1-64): each posting's duplicate checks and SQLite write stay synchronous, only the model wait overlaps, and reports keep source order.
Measured classification calls take about 21 s (p50) and 3,100 tokens, so the request limit binds long before the token limit.
The dashboard's `dev`, `build`, and `start` scripts load the repository-root `.env` through `apps/dashboard/scripts/with-root-env.mjs` (shell variables win); Next.js alone reads only `apps/dashboard/.env*`.
The browser harness launches `next dev` directly, so its runs never inherit the root model settings.
One-off scripts must pass `--env-file-if-exists=.env` themselves.
