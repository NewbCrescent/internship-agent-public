# Repository structure

## `apps/dashboard`

The localhost Next.js App Router control plane. Pages perform server reads through domain services. Mutations live in colocated `actions.ts` files. Reusable UI lives in `components/`, never inline as large page-local components. `scripts/with-root-env.mjs` runs the Next.js CLI for `dev`, `build`, and `start` with the repository-root `.env` loaded. `lib/active-profile.ts` reads the validated local profile cookie, and every page and action passes the selected profile's database to its services. `/resume` edits structured resume entries, and its `preview` route handler streams the current resume as a PDF.

## `packages/domain`

Shared Zod schemas, candidate-fact definitions, provenance types, scope rules, and question-resolution contracts. `submission-mode.ts` holds manual checklist mode and the auto-submit policy with its run blockers. `standing-consent.ts` holds the candidate's standing data-consent and attestation settings and their deterministic whitelist (fact and marketing vetoes, signature and signature-date labels). `fact-options.ts` holds the deterministic rules by which a saved start date, the salary rule, own-expense relocation, background-check willingness, and the graduation date's term pick an offered option. `application-intent.ts` holds the application intent statement schema and the term-standing label for the AI fit. `coursework.ts` holds the coursework file schema (no grades, no IDs), the deterministic "Relevant coursework" answer format, and the course evidence ID and text for the AI fit. It has no database or framework dependency.

## `packages/db`

The only package that opens SQLite or executes SQL. It owns migrations, repositories, profile-specific local data paths, and fictional seed data. The existing database is the demo workspace; the real workspace uses its own SQLite file. `src/requirement-label-hold-repository.ts` (migration 0027) holds postings waiting for AI requirement labels and finds postings whose stored labels may have come from the old rule fallback. `src/application-intent-repository.ts` (migration 0028) stores the candidate's application intent statement. `src/question-alias-repository.ts` (migration 0036) records each exact question wording a stop asked against the saved answer it matched (a fact by key and scope, or a question-memory answer), with no answer value. `src/coursework-repository.ts` (migration 0031) stores and atomically replaces the candidate's relevant courses. `src/mail-match-repository.ts` lists applications for the Gmail watcher's matching. `src/discovery-repository.ts` (migration 0037) also stores imported boards' provenance and each board's fetch health (failure count, last error, retry time).

## `packages/agent`

Application orchestration: candidate workspace operations, deterministic semantic question mapping, safety-policy enforcement, and remembered-answer resolution. `src/workday-session-service.ts` lists Workday career sites with waiting applications and runs the candidate-driven sign-in window for one site. With the account opt-in, `src/workday-account-service.ts` creates, signs in to, verifies, and holds agent-created Workday accounts, preserving create timeout diagnostics through follow-up sign-in; the browser's `src/ats/workday-account.ts` handles a create form's Sign In link that opens the email chooser; `src/workday-account-store.ts` keeps their owner-only accounts file outside the repository and generates passwords; `src/workday-verification-mail.ts` finds the verification link and `src/gmail-mailbox.ts` reads Gmail over read-only IMAP (not exported from the package index); `src/greenhouse-security-code.ts` finds Greenhouse's emailed security code in the same read-only mailbox for `submitBrowserRun` (in memory only); `src/oracle-email-step.ts` takes Oracle Cloud HCM's email step and its emailed one-time code in start, continue, and submit, and `src/oracle-verification-mail.ts` finds that code in the same read-only mailbox (in memory only); `scripts/workday-account.ts` backs `pnpm workday:account`. With the iCIMS opt-in, `src/icims-account-service.ts` takes iCIMS's email-first account step (create or sign in, verify the email, hold), `src/icims-account-store.ts` keeps its owner-only accounts file, `src/icims-verification-mail.ts` finds iCIMS's verification link, and `scripts/icims-account.ts` backs `pnpm icims:account`. `src/standing-consent.ts` builds a run's standing consent inputs, logs each statement accepted or signed under them, and takes Jobvite's Data Consent step. `src/pipeline-orchestrator.ts` advances eligible postings without the candidate (prepare, then optional automatic browser runs that stop at the submit step unless the opt-in auto-submit policy submits a clean run), `src/fit-pursuit.ts` names the unverified requirements of needs-review postings it pursues on AI fit, `src/application-target.ts` applies the domain target (`packages/domain/src/application-target.ts`: term, role, location, AI judgment) to stored postings, `src/list-doorbell.ts` asks GitHub with conditional requests whether a job list changed, and `src/pipeline-schedule.ts` renders the launchd agent and systemd timer. `scripts/pipeline-pass.ts` holds one pass and the watcher's doorbell tick, shared by `scripts/run-pipeline.ts` (`pnpm pipeline:run`) and `scripts/pipeline-watch.ts` (`pnpm pipeline:watch`); `scripts/pipeline-status.ts` and `scripts/schedule-pipeline.ts` back `pnpm pipeline:status` and `pnpm pipeline:schedule`. It also owns the provider-neutral model layer (`src/model/`) — tier-based routing, the OpenAI-compatible client, cost attribution, and the model-backed requirement classifier — and is the only place that decides whether a model participates in ingestion. `src/pass-notice.ts` turns a pass report into the candidate's Discord notice and remembers what was sent, `src/discord-notify.ts` sends it as a DM through Discord's REST API, and `scripts/notify-test.ts` backs `pnpm notify:test`; `src/discord-read.ts` reads the DM thread read-only and `scripts/discord-read.ts` backs `pnpm discord:read`. The Gmail outcome watcher is `src/mail-outcomes.ts` (deterministic outcome rules, application matching, DM text), `src/mail-watch.ts` (IDLE watcher, state, catch-up), and `src/mail-schedule.ts` (systemd service and launchd agent renderers), with `scripts/mail-watch.ts`, `scripts/mail-scan.ts`, and `scripts/schedule-mail.ts` backing `pnpm mail:watch`, `pnpm mail:scan`, and `pnpm mail:schedule`; `src/gmail-mailbox.ts` also provides its IDLE session. `src/requirement-relabel.ts` retries the model labels of held postings each pipeline pass and marks fallback-labelled postings for relabelling; `scripts/hold-fallback-labels.ts` backs `pnpm labels:hold-fallback` (dry run by default). `src/saved-answers.ts` gives browser runs the posting's company and country for company- and country-scoped answers and reads the candidate's saved voluntary self-identification answers; `src/profile-facts.ts` and `scripts/profile-facts.ts` back `pnpm profile:facts`; `src/coursework.ts` and `scripts/profile-coursework.ts` back `pnpm profile:coursework` and build the "Relevant coursework" answer from the saved courses; `src/profile-resume.ts` and `scripts/profile-resume.ts` back `pnpm profile:resume`.

`src/github-job-list-source.ts` reads the five selected 2027 internship indexes without cloning or executing them. It resolves only direct Greenhouse, Lever, Ashby, Workday (`*.wdN.myworkdayjobs.com`), SmartRecruiters (`jobs.smartrecruiters.com`), and Oracle Cloud Candidate Experience (`*.fa[.region].oraclecloud.com`) links to full public postings before discovery hands them to ingestion; unsupported links stay in the source repository for manual review.

`src/posting-page-sources.ts` resolves the remaining list links without a model: Dover (`app.dover.io/apply/...`, its public application-portal job endpoint), iCIMS (`*.icims.com/jobs/{id}/.../job`, the job page's schema.org JobPosting), Workable (`apply.workable.com/{account}/j/{shortcode}`, its public v2 job endpoint), Rippling (`ats.rippling.com/{board}/jobs/{id}`, its public board API), Greenhouse `gh_jid` links on employer domains (board token tried from the company name, then the domain), and any other public career page carrying one schema.org JobPosting in JSON-LD; Lever EU links use `api.eu.lever.co`. `src/host-pacer.ts` spaces requests per host for discovery and `packages/agent/scripts/backfill-posting-dates.ts`. `src/place-text.ts` holds the location-text helpers both resolvers share (joined place parts, ISO country codes named in full, the Greenhouse Office line). `src/discovery-trace.ts` writes the per-listing discovery trace (`<workspace data>/discovery-traces/<date>.jsonl`, kept 14 days) and `scripts/discovery-trace.ts` backs `pnpm discovery:trace`. `src/board-import.ts` and `scripts/import-boards.ts` back `pnpm sources:import-boards` (a reviewed list of public Greenhouse, Lever, and Ashby boards, deduped by kind and slug, at most 300 new per import, `--dry-run` read-only); `src/board-polling.ts` holds the boards' 6-hour interval, failure back-off, and per-pass plan, and `checkPublicBoards` in `src/discovery-orchestrator.ts` checks due boards four at a time with one ingest at a time.

`src/application-record.ts` builds and writes the local PDF record of what each submitted application sent (rendered with `renderHtmlToPdf`, attachments appended by `appendPdfPages` in `packages/browser/src/pdf.ts`); `scripts/application-record.ts` backs `pnpm application:record`.

`src/daily-digest.ts` builds and sends the once-a-day Discord digest (what waits on the candidate, numbered; sends and company replies since the last digest) from the watcher tick in `scripts/pipeline-pass.ts`; `scripts/digest-preview.ts` backs `pnpm digest:preview [--send]`.

`scripts/pipeline-audit.ts` backs `pnpm pipeline:audit`, the read-only `--trace` path and its optional tmux watcher. `src/application-holds.ts` classifies and reconciles current job and run holds, distinguishing uncertain submits from field errors that need candidate action. `packages/db/src/application-hold-repository.ts` and migration 0033 keep the revision history, receipt checks, and separate manager and candidate delivery acknowledgements. The pass notice and digest share those candidate revisions.

`src/submission-receipts.ts` checks for a specifically matched employer receipt before an uncertain attempt can be reopened. It runs in the normal Gmail scan and in the single-run `mail:scan --receipt <ref>` catch-up. The receipt proof stays private and does not set application status.

`src/automatic-retry.ts` retries automatic runs a since-fixed bug held (cancel the run, send its job back to READY_FOR_REVIEW for the next pass) and, with `--reopen-unsubmitted`, reopens a failed submit with a fresh no-match receipt check and positive noncompletion evidence (Greenhouse's security-code email or step, or post-submit evidence the site never took the click: Ashby's busy notice, Dover's Turnstile, or an older capture of the intact form, judged by the pure `src/unsubmitted-evidence.ts`); with `--close-unsubmitted` it closes a never-clicked failed submit on a posting its evidence shows closed (run cancelled, job skipped as "Posting closed"); with `--correct-submitted --confirm` it corrects a SUBMITTED record that rests only on the closed-dialog relabel, leaving a failed run held as a possible submission; with `--verified-hold` it atomically requeues one eligible pre-submit fault at its reviewed revision (`--run`), or releases one job-level automation fault on a job with no live run and no submit attempt (`--job`); with `--held` it also releases Workday account holds the account step left as "unexpected" (no run was saved for them); it backs `pnpm pipeline:retry` (`scripts/pipeline-retry.ts`). `src/continued-auto-submit.ts` picks the pipeline-started runs at the submit step that the auto-submit policy may still take on a later pass (answered since their start pass, or held earlier only by the target, the AI fit, or a cap) and words what `pnpm run:answer` prints when a continued run reaches the submit step.

`src/submit-evidence.ts` writes and reads post-submit evidence (the screenshot, redacted visible text, query-stripped URL, and invalid fields a submit click left when no confirmation was recognized; local, mode 600, never sent anywhere) and Workday evidence (a step Workday would not save, for the run; an account-step stop, for the job, with no run) and covering-dialog evidence (once per run, the first field a modal dialog over the form leaves unfilled: the dialog's redacted text, role, aria attributes, and button labels, read by `readCoveringDialogsIn` in the browser's `src/announcement-dialog.ts`); `scripts/run-evidence.ts` backs `pnpm run:evidence --run <ref>` and `--job <ref>`.

`src/company-policy.ts` reads application history for the automatic pipeline's per-company limits (automatic applications per target term and the one graduation profile per company); the pure identity, cap, and pin rules live in `packages/domain/src/company-policy.ts`, and `packages/db/src/company-history-repository.ts` lists postings that reached a browser run or a submission.

`src/question-answers.ts` decides whether a held run's answer goes to candidate facts, to question memory, or is used once (and why), and reads saved answers for field resolution; `src/run-answer.ts` backs `pnpm run:questions`, `pnpm run:answer`, and `pnpm profile:answers` (`scripts/run-questions.ts`, `scripts/run-answer.ts`, `scripts/profile-answers.ts`). The normalization and never-save rules live in `packages/domain/src/question-answer-memory.ts`, and `packages/db/src/question-answer-repository.ts` (migration 0032) stores the answers. `src/pause-recheck.ts` holds the stop re-check's helpers (which stops it looks at, recorded-wording resolution that never widens a saved answer's scope, match kinds, the timeline line); `recheckRunPauses` and `recheckPausedRuns` in `browser-orchestrator.ts` re-plan held runs' open stops against the saved answers after every saved answer, and `scripts/questions-recheck.ts` backs `pnpm questions:recheck` (dry run read-only, `--apply` under the pipeline lock). `src/pause-review.ts` runs the AI review of a run's pause batch (one model call per batch, task `application.pause_review`) behind deterministic guardrails: a saved-answer match is applied only when every check passes (it does not hold auto-submit, and the approval names the question), other questions get the model's reason, and a suggested draft is shown, never filled or stored, and holds the run until the candidate answers it.

## `packages/voice`

The candidate's writing-voice tools, ported from the Codex `my-writing-voice` skill: the local corpus loader (reference set only; the evaluation holdout is never loaded), example selection, the quantitative style audit with corpus-overlap detection, and the client for the local three-detector voice gate. Pure logic plus file and subprocess access; no database or model calls. `packages/agent/src/voice-drafting.ts` runs the drafting loop.

## `packages/github`

Read-only GitHub REST ingestion, bounded file selection, deterministic evidence extraction, incremental blob-SHA synchronization, and evidence-review orchestration. It may call `packages/db` repositories but never executes repository content.

## `packages/jobs`

Posting ingestion and normalization: text normalization that defines the span coordinate system, deterministic extraction of requirements, technologies, locations, compensation, and stated constraints, plus the `RequirementClassifier` interface. It depends on no model provider, so its suites run offline by construction. `place-names.ts` reads location pieces as countries, US states, or Canadian provinces, and `extraction-backfill.ts` re-reads location and pay from stored snapshots (`packages/agent/scripts/backfill-extraction.ts`, `pnpm backfill:extraction`).

## `testing-harness`

Manifest-driven agent verification. Pure tests, temporary-SQLite integration, browser workflows, runner support, and workflow self-tests are separated by tier and feature. `support/gate-slots.mjs` is the machine-wide gate-slot semaphore that `agent-finish.mjs` and the browser-tier suites `run.mjs` starts take a slot from (`INTERNSHIP_AGENT_GATE_SLOTS`, default 2), with lock files in the per-user temp directory.

## `docs/technical`

The technical guide, split so parallel runs edit different lines: one folder per topic (`NN-<topic>/`, listed with its title in `TECHNICAL.md`), one file per paragraph (`NNN-<slug>.md`, read in name order), and one sentence per line. New material goes in a new file numbered between its neighbours, or in a new sentence beside the sentences about the same feature; only a new topic folder edits `TECHNICAL.md`.

## `bugs`

Confirmed defects, one file per bug: `open/<slug>.md` until it is fixed, then moved with `git mv` to `resolved/<slug>.md`. The slug is the title in lower-case words joined by hyphens, and the file starts with `# <title>`. Bugs are not numbered, and `BUGS.md` only describes this layout, so filing or resolving a bug never edits a shared line. A bug file may end with a `## Refuted causes` section, one `- <theory>. Evidence: <...>` entry per disproved theory, and states how its fixture was made on a `fixture: modelled` or `fixture: captured <date>` line.

## `scripts`

`public-sync.mjs` (`pnpm public:sync`) builds the public mirror: it exports a ref's tracked files, drops private-only paths, puts `PUBLIC-README.md` in place of `README.md`, scrubs the rest with the Git-ignored deny-list `data/public-scrub.json`, scans file contents and file names for leftovers and secrets (failing closed), and syncs the result into a local clone of the public repository. Its regressions are in `testing-harness/harness/public-sync.test.mjs`. `split-docs.mjs` is the one-time migration that split the single-file `TECHNICAL.md` and `BUGS.md` into `docs/technical/` and `bugs/`; `--check` proves the split lost nothing, and `--write` runs only on the pre-split files (the split's own merge rounds), never after runs have edited the new folders. Its regressions are in `testing-harness/harness/split-docs.test.mjs`, and `docs-layout.test.mjs` keeps `TECHNICAL.md` and `BUGS.md` index-only.

## `data`

Git-ignored local runtime data. Only `.gitkeep` is tracked. The existing `internship-agent.sqlite` file is the demo workspace; `profiles/real/internship-agent.sqlite` stores the real workspace. Browser-run files, base resumes (`resumes/`), the transcript (`documents/`), rendered resume PDFs, and the persistent `browser-profile/` use the same separate profile directories. Never place real candidate data in fixtures or reports.

Dashboard list reads use `packages/jobs/src/dashboard-list.ts` and `packages/agent/src/resume-refresh.ts`, backed by bounded repository queries and migration 0023 read indexes. Shared page bounds live in `packages/domain/src/list-pagination.ts`; `apps/dashboard/components/layout/ListPagination.tsx` renders pagination. `app/loading.tsx` and the shell's separate profile Suspense boundary provide navigation feedback.

`apps/dashboard/app/styles.css` is the dashboard's only stylesheet: neutral design tokens on `:root`, a zero-specificity base style for every button and form control, and variant classes (`primary-button`, `secondary-button`, `danger-button`, `review-button`, `text-button`). `components/layout/NavLink.tsx` marks the current sidebar page, and `components/layout/PostingFilterFields.tsx` holds the country and minimum-pay controls shared by the Jobs and Review toolbars. The Review focus view is built from `packages/domain/src/review-focus.ts` (settings schema, filter, and ranking), `packages/db/src/review-focus-repository.ts`, and `packages/agent/src/review-focus.ts`, and rendered by `components/applications/ReviewCard.tsx`, `QuickSkip.tsx`, and `FocusSettings.tsx` with `lib/review-facts.ts` for pay and age text. `testing-harness/dashboard/style-contracts.test.ts` keeps rendered class names and the stylesheet in sync.

Review Queue sort/day URL validation lives in `packages/domain/src/review-queue.ts`; the application repository filters employer dates and joins stored fit scores before counting and slicing pages. `components/applications/ReviewQueueControls.tsx` provides sort and age inputs, while shared pagination preserves those options.

Hybrid fit contracts live in `packages/domain/src/matching.ts`; `packages/matching/src/semantic-fit.ts` validates citations and AI competitiveness contracts (with legacy coverage support). `packages/agent/src/model/semantic-fit.ts` builds full-posting, candidate context (intent and level), and approved academic/resume/evidence and saved-course (`course:<CODE>`) model inputs and orchestrates automatic or explicit calls. `packages/db/src/semantic-fit-repository.ts` and migrations 0024–0025 own local caches, algorithm versioning, invalidation and failure tracking; migration 0034 limits fact-driven invalidation to `FIT_CONTEXT_FACT_KEYS` (packages/domain `matching.ts`). `components/jobs/AiFitButton.tsx` retries analysis, while MatchPanel and Review show the score's basis. The matching suites include deterministic provider doubles; `testing-harness/matching/semantic-fit-model.acceptance.ts` is the explicit synthetic live-provider smoke.

## `.claude/skills`

`.claude/skills/scout-swarm/` holds the scout-swarm skill, which fans out read-only scouts over many independent targets (job boards, sources, sites, listings) and then merges, de-duplicates, and spot-checks their results into one JSON file that is never written to real data directly.
