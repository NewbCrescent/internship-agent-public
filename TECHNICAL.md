## Stack

- pnpm workspaces and Turborepo
- Next.js App Router with TypeScript
- SQLite through Node's built-in `node:sqlite`
- Zod runtime contracts
- Vitest for pure and local integration suites
- Playwright for critical browser workflows

No cloud service or model provider is required for Milestones 0–1. Milestone 3 works fully offline as well; a model provider only improves requirement classification.

Milestone 2 uses the versioned GitHub REST API through native `fetch`. Public access needs no credential within GitHub's unauthenticated rate limit; an optional local `GITHUB_TOKEN` raises the read limit. Repository code is never cloned or executed.

Milestone 3 ingests pasted posting content plus the candidate's supplied URLs. It does not fetch Handshake or any ATS; authenticated capture belongs to Milestone 7's browser worker, which will feed the same ingestion entry point.

## Runtime flow

```text
Dashboard page -> domain/application service -> SQLite repository
Dashboard form -> Server Action -> Zod validation -> service -> repository
Question -> deterministic mapper -> policy gate -> scoped fact lookup -> resolution
Evidence page -> Server Action -> GitHub evidence service -> GitHub REST read + SQLite repositories
Jobs page -> Server Action -> agent orchestrator -> jobs normalization -> SQLite repositories
Jobs page -> Server Action -> agent match orchestrator -> matching eligibility + fit -> SQLite match reports
Jobs page -> Server Action -> agent application orchestrator -> writer package -> verifier gate -> SQLite packages, resume variants, event log
Applications page -> Server Action -> agent browser orchestrator -> sign-in check -> fill -> upload (Handshake base PDF or rendered variant PDF) -> approval-gated submit
Profile page -> Server Action -> base resume service -> profile data directory + SQLite checksum row
Resume page -> Server Action -> resume entry service -> SQLite entry revisions; /resume/preview route -> structured resume -> Chromium PDF
Profile page -> Server Action -> Connect Handshake -> visible browser window -> URL-only sign-in state -> SQLite browser_sessions
```

The dashboard uses Server Components for reads and Server Actions for mutations. Client Components are limited to interactive forms and receive serializable data.

## Dashboard navigation

Overview reads only the 20 newest posting summaries. Applications and Review use validated, clamped `?page=N` parameters with 50 entries per page and stable id tie-breakers. Application status filters run before pagination; aggregate pipeline and outcome totals remain workspace-wide. Review defaults to fit high-to-low (unscored last, newest import then id for ties) and offers Newest by import time. `?sort=fit|newest&days=N` combines sort and an employer publication age of 1–365 days before its SQL count and pagination; the rolling window includes both boundaries and excludes unknown/future dates. Page links preserve these options; changing a control resets to page 1. Cards show stored fit scores and employer dates, and an empty filtered result is distinguished from an empty queue. Both Jobs and Review also take `?country=XX|none&minPay=N`, validated in `packages/domain/src/posting-filters.ts`: a posting matches each country it states, and minimum pay compares USD per hour against the top of the stated range, converting monthly and yearly pay at 2,080 hours a year in one SQL expression (`packages/db/src/posting-filter-sql.ts`) shared by the Review query and the Jobs summaries. Postings without a stated country or comparable USD pay are hidden by those filters and counted in the toolbar; "Not stated" lists the countryless ones. Country labels are computed on the server. The Jobs pager keeps the window position and shows a pending state instead of scrolling to the top. Reads do not recompute fit. Review compares only the visible page's latest frozen resumes. Batch checkbox selections are page-specific; **Refresh all** resolves changed applications across the entire queue, including entries hidden by age filters, in its Server Action, retaining the existing approval and submission safeguards. With `INTERNSHIP_AGENT_MANUAL_ONLY=1`, the Review Queue becomes a manual checklist: package approval, browser runs, and submit approvals are hidden and refused at their entry seams (nothing is removed; unset the flag to restore the AI flow), and checking an entry off (one click and a confirmation on its card) records a terminal candidate-applied `SUBMITTED` with no undo.

Review opens on a focus view (`?view=all` keeps the full queue and its controls). The focus is one row in `review_focus` (migration 0026), validated by `packages/domain/src/review-focus.ts` and kept apart from `candidate_preferences`, whose triggers bump the AI-fit context version and would mark every AI score out of date. It keeps postings whose title category is in the focus (software engineering always), that state a focus country or (by default) none, that were posted within the window (default 14 days), and whose stated USD pay meets the optional minimum; an unknown date or unstated pay never hides a posting. Focus entries rank by AI fit (unscored last), then stated USD pay, then the newer posting, filtered and sorted in the agent over the whole queue before paging. Each card shows pay, place, age, AI score, and category on one line, and links straight to the application (`applicationUrlFor`), the latest prepared resume PDF, and a two-click "Not for me" whose fixed reasons are recorded as the skip reason.

Migration `0023_dashboard_read_indexes.sql` indexes location, latest-resume, posting order/status, and recent-event reads. Pipeline counts use a SQL aggregate rather than materializing summaries; Applications reuses its outcome statistics for recommendations. The root loading boundary shows navigation feedback, and the shell's profile cookie read has its own Suspense boundary so navigation links can render independently. Jobs retains its existing 50-card page and publication-age filter.

The dashboard gate includes the existing disposable-SQLite job-list suite with a 2,000-posting pagination/count scenario and browser checks for tab navigation, URL history, status preservation, bounded rows/checkboxes and response size, global resume refresh, and Review fit/age ordering and boundary cases. Timing on a real development workspace is observational and excludes first compilation; browser tests check behavior rather than enforcing a machine-specific latency budget. The fast `dashboard-style-contracts` suite (`pnpm test:dashboard:fast`) parses every dashboard TSX file and fails when a rendered class name (including both branches of a conditional) has no rule in `app/styles.css`, or when buttons without a class would fall back to the browser default.

## Data model

Each local workspace has its own SQLite file and one candidate ID. The existing `data/internship-agent.sqlite` is the fictional demo; `data/profiles/real/internship-agent.sqlite` holds the real profile and its jobs, evidence, applications, and outcome history. The browser stores only the validated `real` or `demo` selector in a local HTTP-only cookie, defaults to real, and passes the selected database explicitly through every page and action. `candidates` stores that workspace's editable profile. `candidate_preferences` stores typed role, location, work-mode, and graduate-internship exclusion preferences; those values never imply an application answer. The exclusion is disabled by default and stored independently in each workspace (migration `0016_graduate_internship_preference.sql`).

`candidate_facts` is append-only by revision. A current fact is identified by candidate, semantic key, and normalized scope. Updating a fact supersedes the prior row in one transaction. Each revision stores its typed JSON value, source, source detail, confidence, sensitivity, reuse policy, and timestamps.

Facts use structured scopes:

- `global`
- `country` (work authorization, sponsorship, and relocation willingness)
- `location`
- `application_channel` (only `handshake_internal`, and only for `graduation_date`)
- `company` (the posting's employer, normalized: lower case, punctuation dropped, trailing legal suffixes such as Inc or LLC removed; exact match, never fuzzy; only `previously_worked_here` and `relatives_at_company`, whose Yes must be company-scoped)

`enrolled_full_time` is a global yes/no the candidate enters through candidate memory ("Are you a full-time student?"); questions that pair full-time with student, enrolled, or enrollment map to it, while full-time work questions do not. It is never set on the candidate's behalf.

Context-specific resolution requires an exact scope. There is no automatic fallback from location-specific to global or between locations. The one fallback is one-way: a question asked on an alternate-profile application (a Handshake Quick Apply / Apply posting with `application_type = HANDSHAKE_INTERNAL`, or any browser run whose form asks for a transcript) uses the `handshake_internal` answer and, when none exists, the global answer. A Handshake-only answer never answers a global question, an external ATS, an employer site, or an unknown application type. Eligibility applies the same order for graduation windows, but only by posting type: a transcript requirement is known only once the application form is open, so eligibility for other postings uses the global answer. A second one-way fallback covers company-scoped questions: a question about the posting's employer uses that company's answer and, when none exists, the global answer; a company answer never answers another company or a global question (browser runs pass the posting's company through `postingQuestionContext`). Relocation is recorded per country: a named place readable as a country (`readPlace`: "Austin, TX" is US; a bare city stays a location scope), else the question's own country words, else the posting's one stated country. No country, or a country without an answer, pauses; the legacy global relocation answer never answers a question (eligibility reads the location's answer, then the posting location's country, then global). Work-authorization and sponsorship questions take the same order without the place reading: a pause answer's country, else the question's own country words, else the posting's one stated country ("Will you require future sponsorship?" on a US posting is `requires_sponsorship` for US); a posting with no country or several stays AMBIGUOUS.

`candidate_coursework` (migration 0031) holds the candidate's relevant courses: one school plus, per course, its code, title, term, and status (`completed` or `in_progress`), in the candidate's order, with provenance "candidate-confirmed from transcript" (`source = 'candidate_confirmed_transcript'`). It is written only with `pnpm profile:coursework`, from a list the candidate gives; courses are never inferred. It holds no grades and no student ID, and the transcript file itself is never parsed. Its triggers bump the AI-fit context version (0024), so a changed set re-scores every AI fit.

`github_repositories` stores repository identity and observed/analyzed SHAs. `repository_files` stores the current bounded selection's blob and content hashes. `projects` owns stable project profiles. `evidence_items` stores immutable commit/path/line/excerpt provenance. Stable `claims` point to append-only `claim_revisions`, and `claim_review_events` records explicit allow/question/reject decisions.

Review status and source freshness are independent. Only `ALLOWED` plus `CURRENT` claims are verified. A changed evidence fingerprint creates a pending revision; deleted supporting paths make the current revision stale. Same-SHA sync is a no-op, and a new SHA fetches only selected blobs whose blob SHA changed.

## Job posting model

`jobs` holds posting identity, the derived application type, and the full application state machine. `job_snapshots` stores the immutable normalized posting text; re-ingesting identical content is a no-op, and changed content supersedes the prior snapshot and re-derives every dependent row in one transaction. A stored posting retains its source URL as its revision key. Discovery also checks current snapshots across URLs: matching normalized company, title, and full posting text is counted as a duplicate and is not ingested or analyzed again. Distinct descriptions under one company and title remain separate postings. Dashboard posting lists and overview counts include only jobs with a current snapshot, so legacy pre-normalization placeholders are retained without being parsed as postings.

`job_requirements`, `job_technologies`, `job_locations`, `job_compensation`, and `job_constraints` each carry a character span into the current snapshot. Ingestion re-verifies every span against the snapshot text and drops any that does not match, so a stored field always quotes text the posting actually contains. Public board HTML conversion preserves list items as bullet lines before normalization. Deterministic extraction reads those bullets and also applicant-directed prose sentences with their own explicit hard or preferred cue; general prose and section headings alone do not become requirements. A guarded requirement repair can replace only requirement rows for the expected current snapshot while a posting is still in a pre-preparation status; it verifies every replacement against the stored text and leaves the snapshot and other derived rows unchanged. For a hard Master's- or doctorate-only requirement, subject overlap with an undergraduate degree does not establish eligibility: the match needs candidate review unless recorded degree evidence establishes the required level. When the candidate enables graduate-internship exclusion, matching fails internships or co-ops with an explicitly Master's/PhD-targeted title or a stated hard graduate-degree requirement lacking an explicit bachelor's alternative. Preferred graduate study and unrelated prose mentions do not trigger this preference. The match reason identifies it as a saved preference, not a candidate fact.

Locations are read from US "City, ST" pairs anywhere in the text and, on a labelled line ("Location: …") or a line that is nothing but a place, from full US state names, Workday's "US-State-City" form, Canadian provinces, and "City, Country" or "Country, City" with country names taken from the runtime's ISO 3166 region names (`packages/jobs/src/place-names.ts`). An explicit country wins, then a full state name, then a province, then a two-letter state code, so "Toronto, ON, CA" is Canada. When a labelled line or place line names no country, state, or province, a short table of unambiguous well-known cities decides (`readWellKnownCity`: "Berlin" is Germany, "Paris" France, "South San Francisco" and "NYC" the US; parentheses and words such as Hybrid, Remote, Office, HQ, Area, Metro, and Greater are ignored around them); "City, ST" and an explicit country always win ("Paris, TX" is the US, "London, Ontario" Canada), ambiguous names (Cambridge, Waterloo, Johnston, Durham, Vancouver) are left out, any other bare city stays unknown, and a place mentioned in prose never becomes a location. `locationCountryCodes(text)` reads one location string the same way. Discovery writes structured ATS location fields into the `Location:` line (`packages/agent/src/github-job-list-source.ts`): Ashby's location joined with its `address.postalAddress` locality, region, and country (a work-mode-only location such as "Hybrid" gives way to the address; secondary locations follow after "; "), Lever's `allLocations` (else the category location) with the posting's ISO `country` named when there is one location ("Seoul, South Korea"), Greenhouse's offices as a second `Office:` line when they say more than the location, and Workday's country joined to a single location. The GitHub list's own column is added as `Job list location:` when the board states no location or one that names no readable place. No posting source reads HTML (every source is a JSON API), so there is no JSON-LD `jobLocation` to read. Postings stored before this keep their old snapshots; `pnpm backfill:extraction` re-reads them with the city table. Pay reads trailing units including "-ly" forms ("$45.00 - $55.00 hourly"), ranges joined by dashes, "to", or "and", a leading pay label ("Hourly Rate Band $35 — $55 CAD"), and a currency code before or after the amount; a bare "$" stays USD. `pnpm backfill:extraction [--profile real|demo] [--apply]` re-reads location and pay for every stored snapshot with the current extractor under the pipeline lock: a dry run reports coverage before and after, postings that would lose a country or USD pay, and samples; `--apply` replaces only `job_locations` and `job_compensation` rows in one transaction, re-verifying every span, and leaves snapshots, requirements, matches, packages, and statuses alone. No network or model is involved.

Three states stay distinct, because Milestone 4 eligibility depends on the difference:

- a `STATED` value the posting asserts at a recorded span;
- an `INFERRED` reading, which can never be a hard requirement — enforced by the domain schema and by a `CHECK` constraint on `job_requirements`;
- an absent value, meaning the posting is silent. Silence is never converted into a decision.
Separately, stated soft-trait skill and non-tenure experience requirements naming no concrete tool, method, credential, quantity, or tenure span pass by policy as non-discriminating rather than pausing verdicts; mixed, technical, degree, and tenure ("2+ years", "several years") wording stays on the evidence path.

`job_constraints` holds one row per stated constraint only. A posting that does not mention sponsorship has no sponsorship row, which is not the same as sponsorship being unavailable. A constraint's text (`raw`, at most `STATED_CONSTRAINT_MAX_LENGTH` = 600 characters) is the matched sentence; a longer "sentence" (no period or newline, such as comma-joined clauses) keeps a window of at most 600 characters from 200 before its keyword, with a span over exactly that window, while the decision (dates, country, requires or offers) is still read from the whole sentence. Rows stored before the window have their raw text (and a span over 2,000 characters) clipped on read (`clipStatedText`), so the posting still parses and its analysis runs.

`pnpm pipeline:run [--profile real|demo] [--skip-discovery]` (root `.env` loaded) is the unattended pass: it checks every enabled discovery source, then `advancePipeline` prepares every eligible QUALIFIED posting (and, with a target, the needs-review postings described under **Needs-review postings on AI fit**) and, with `INTERNSHIP_AGENT_AUTO_APPLY=1`, starts one automatic browser run per clean READY_FOR_REVIEW package that has no run. An automatic run replaces the package approval, never the submit approval: it opens the candidate's persistent, visible browser at `applicationUrlFor(posting)` (Lever `/apply`, Ashby `/application`, otherwise the posting or external application URL), fills known answers, and stops at `awaiting-approval` or `paused-needs-input`. It records "started automatically" rather than an APPROVED event. Before filling, an automatic run stops on any field labelled as a password (sign-in or account creation, which the agent never performs) and on pages with no recognizable form fields; the stop is logged once as "Automatic browser run needs you: …", the job stays READY_FOR_REVIEW, and the pipeline does not retry it. Any other failure is logged as "Automatic browser run failed: …" (up to 500 characters) and retried on the next pass; `--retry-stopped` also retries earlier "needs you" stops for one pass. Before reading a form, the Playwright adapter waits (up to 15 s) until visible controls exist and their count holds for 1 s, because client-rendered forms such as Ashby draw their fields after load. Recognition trims labels to 300 characters, ids to 200, and select options to 500 of 200 characters each rather than rejecting a real form, and types `input[type=number]` as `number`, which the planner fills only with a purely numeric value (otherwise it pauses; a date is never reformatted to fit). A single year, month, or day box labelled "start date" is not mapped to the availability date. The Playwright adapter installs a no-op `__name` in each page (now and on every navigation) because tsx compiles with esbuild keepNames, whose helper would otherwise be missing inside functions passed to `evaluate`. `pnpm pipeline:run` holds `<workspace data>/pipeline.lock` (`{ pid, startedAt }`, created atomically) for its whole run and releases it on exit, Ctrl-C, or SIGTERM. While a live process holds it, a second pipeline run refuses to start, the Jobs page disables every Check board button with a note, and the board-check action refuses on its own (covering stale pages); adding a board stays available. A lock whose process has exited is stale and ignored. The review queue also lists APPLYING jobs whose latest run awaits approval or input. Before preparing, `advancePipeline` analyzes any DISCOVERED posting that has no match report, so postings stranded by an interrupted discovery run are not skipped forever by known-link filtering.

**Target, auto-submit, and the list doorbell.** `INTERNSHIP_AGENT_TARGET_TERM` (for example `summer-2027`) narrows the automatic pipeline to postings `judgeTargetPosting` (packages/domain `application-target.ts`) does not skip: the term (a title naming the target season, or one silent on term whose description names no other; another season, year, off-cycle month with a year, H1/H2, co-op, or a placement longer than a summer skips; the target season beside another term or a co-op goes to review), a software or adjacent role from the title (software, full-stack, mobile, ML/AI, data engineering or science, infrastructure, SRE, security engineering; analyst-only, product, design, sales, hardware, research-scientist, and graduate-degree titles skip), a stated US location (another country skips; none stated goes to review), and the source (`judgeSource`: a posting whose source or apply link is on Handshake by `isHandshakeHost` in packages/jobs, or whose type is `HANDSHAKE_INTERNAL`, skips with "Source: Handshake is out of scope (GitHub lists only)."; the Handshake session code and dashboard panel stay in place). `judgeFit` then reads only a current AI assessment (a stale or missing one, or the keyword estimate, never qualifies): below the skip line (50, or the auto-submit bar when it is set lower, never below 40) skips; below the bar, LOW confidence, a WEAK rating, or a gap naming a degree level goes to review; a MODERATE or STRONG judgment at or above the bar may be submitted (user, 2026-11-19). Off-target postings get no AI call and are not prepared, in discovery and in the pipeline; the pipeline logs "Not pursued for your target: …" once per posting. `INTERNSHIP_AGENT_AUTO_SUBMIT=1` (with auto-apply and a target; manual checklist mode always turns it off) submits a run right after the automatic fill when the combined decision is `apply`, `autoSubmitBlockers` finds nothing (no open pause, safeguard, voice-drafted answer, kept attachment, or site type the classifier did not recognize itself), and the configured daily cap has room. Set `INTERNSHIP_AGENT_AUTO_SUBMIT_DAILY_CAP=unlimited` to remove the total daily cap. Per-company limits and the graduation-profile rule still apply. A numeric setting (default 10, clamped to 1–50) counts automatic approvals logged since local midnight (`automaticSubmissionsSince` in `pipeline-orchestrator.ts`: each approval belongs to its job's latest run created at or before it, and is released only when that run is known not to have reached the site, that is, its approval was withdrawn (field errors after the click, a challenge, a missing security code) or the failed submit was reopened with `--reopen-unsubmitted` before the job's next run began; a submitted, submitting, failed, cancelled, or still-approved run, or an approval with no run found, counts); `INTERNSHIP_AGENT_AUTO_SUBMIT_MIN_FIT` (default 50, clamped 40–100) is the AI bar. `approveRunSubmissionAutomatically` records "Submission approved automatically by your auto-submit policy: …" with the basis (which names the AI fit, its rating and confidence, and the bar it met), never an APPROVED event, and `submitBrowserRun` then submits with the usual confirmation check. A failed automatic submit is logged ("Automatic submission failed: …") and never retried. A run the pipeline started that reaches the submit step clean later (its last question answered with `pnpm run:answer` or on the application page, or held earlier only by the target, the AI fit, the company cap, or the daily cap) is taken up again at the start of each later pass's browser step (`continuedAutoSubmitRuns` in `packages/agent/src/continued-auto-submit.ts`; candidate decision 2026-11-21) and goes through the same `submitAutomatically` check and submit; the graduation-profile rule is re-checked there against the company's pinned profile, and an answered run's approval basis says some answers were the candidate's own for that run. The sweep takes only the latest live run of an APPLYING job, started by a "started automatically" event (never a run the candidate started, nor one with no start event), with no other live run, no run blocker, no submit approval, no automatic approval logged since the run was created, no post-submit evidence, confirmation, or confirmed receipt, no active possible-submission hold, the same verified package, AI requirement labels, and a qualified (or pursued-on-fit) verdict; auto-apply off or manual checklist mode skips it. **Needs-review postings on AI fit.** At the candidate's request (2026-11-24), `advancePipeline` also prepares an ANALYZING posting whose deterministic verdict is NEEDS_REVIEW when `reviewPursuit` (packages/matching `review-pursuit.ts`) allows it and a target is set: the match is eligible with no failed finding; every open finding is a skill or experience neither evidence nor the resume names, degree wording the reader cannot compare, or a B.S./B.A. mismatch; no open finding, requirement (required or preferred), or title names graduate-only study; no open requirement is a statement of fact (clearance, citizenship, U.S.-person or export-control status, work authorization, sponsorship); the job has no package and no browser run; and the combined target decision (term, role, US location, source, and `judgeFit` at the auto-submit bar, 50 by default, or 80 when auto-submit is off) is `apply`, which needs a current AI fit at or above the bar. **Daily digest.** With the same Discord settings, each watcher tick (`runWatchTick`, whether or not a list changed; skipped while another pass holds the lock) calls `dailyDigestTick` in `packages/agent/src/daily-digest.ts`, which sends one short DM at or after 09:00 local time, at most once per local day. **Gmail outcome watcher.** `pnpm mail:watch [--profile real|demo] [--since 3d]` is a long-running listener, not a poll: `pnpm mail:schedule install|remove|status` installs it as the systemd user service `com.internship-agent.mail.<profile>` (`Restart=always`, `WantedBy=default.target`) or a launchd `KeepAlive` agent, and refuses to install without the Gmail and Discord settings. The first run starts at UIDNEXT (or at most `--since` back); a UIDVALIDITY change restarts from new mail without a flood; every connect runs a catch-up round over UIDs above the last one; reconnects back off from 5 s to 5 min; an auth failure DMs once ("Gmail access stopped working; check the app password") and waits 30 minutes. Only bodies of mail from ATS, assessment, or scheduling domains or from a company the candidate applied to are read (at most 64 KB, in memory only). `src/mail-outcomes.ts` classifies deterministically (rejection, then offer, then assessment, then interview, then recruiter reply; a subject naming a security code, verification code, one-time code, or "verify your account", or a would-be recruiter reply whose body names a security or one-time code, is a `verification` email instead; receipts, other account emails, newsletters, and job boards are ignored) and matches by sender domain, ATS tenant, sender name, subject, or body against submitted applications first, then ones the agent started (APPLYING or with a browser run). Only matched mail is DMed: category (assessments first, marked urgent, deadline first), company, title and job reference, the redacted subject, and the sender domain. An unambiguous match also gets the timeline note `Email received: …` (no status change). A `verification` email is machinery, not a company reply: it is never DMed and the daily digest never counts it (nor an older "Recruiter reply" note whose subject names such a code), but it still gets the note `Email received: Verification code from <domain>: "<subject>"` (code-like tokens in the subject replaced by "[code]"; the code itself is never kept), which the `--reopen-unsubmitted` evidence reads. Body text never appears in DMs or logs and nothing goes to a model. A failed DM is retried on the next round without advancing. `pnpm mail:scan [--since 7d] [--dry-run]` is the manual catch-up and debug tool with the same rules; it never moves the watcher's UID position. Logs (state only) go to `<workspace data>/mail-logs/`.

**Retrying held automatic runs after a fix.** `pnpm pipeline:retry [--profile real|demo] (--run <id or 8-character prefix> ... | --held) [--dry-run] [--start] [--reason "<text>"]` (`packages/agent/scripts/pipeline-retry.ts`, logic in `src/automatic-retry.ts`) re-runs automatic runs a since-fixed bug held, instead of continuing them with their old pauses. `retryAutomaticRun(database, runId, { reason })` accepts only a run the pipeline started (`runStartedByPipeline` over the job's APPLYING events) whose status is `paused-needs-input`, `awaiting-approval`, or `failed`, on a job still APPLYING with no other run that is not cancelled; it refuses a run with any answered pause, a run with `submissionApprovedAt` set (which also covers every failed submit: refused, challenged, or unconfirmed submits keep their approval and stay refused), and any application with a submitted or submitting run. A run the site refused with field errors after the submit click (see Post-submit outcomes) is paused with its approval withdrawn, so it is retryable unless one of its pauses was already answered (then continue it with `pnpm run:answer`). It cancels the run, moves the job from APPLYING back to READY_FOR_REVIEW, and logs "Automatic run retried after a fix: <reason>" (default reason "the bug that held it is fixed."). The next pass then starts a fresh automatic run under the current code, logged "started automatically", with the company cap, profile lock, target, and fit rules applied as usual; an automatic stop ("needs you") logged before the job's latest retry no longer blocks it, while a stop after the retry does. `--run` takes one or more references (repeat the flag or list several), `--held` takes every held (paused or awaiting-approval) run on an applying job, and the command prints one line per run, `retried …` or `skipped … (<reason>)`, then a count. It holds the workspace's pipeline lock (it refuses while a pass holds it, and in manual checklist mode) and notes when auto-apply is off; `--dry-run` prints `would retry …`, writes nothing, and takes no lock. `--start` (not with `--dry-run`) then runs one pass with no discovery, like `pnpm pipeline:run --skip-discovery`, in the same process while still holding the lock (`runPipelinePass({ lockHeld: true })`, which refuses unless this process holds the lock); it runs no pass when nothing was retried. The pass opens the visible browser, so on the PC run it as `xvfb-run -a env -u WAYLAND_DISPLAY pnpm pipeline:retry --held --start`. A failed submit stays refused, except through the explicit override `pnpm pipeline:retry --run <ref> ... --reopen-unsubmitted --reason "<text>" [--dry-run] [--start]` (`reopenUnsubmittedRun`; `--held` and the default reason are not allowed with it): it reopens a `failed` run whose submit was approved (so clicked) only with positive evidence that the site did not complete it (`unsubmittedEvidence`): a timeline event "Email received: <label> from <greenhouse-mail.io or greenhouse.io domain>: \"Security code for your application to <Company>\"" naming the posting's company, logged after the approval and within 24 hours of it (any label: the watcher's Verification code note, or the Recruiter reply note older watchers wrote), or a stored post-submit evidence capture with the `verification-code` outcome. It refuses a run with a recognized confirmation, a run never approved, a paused or submitted run, a run the candidate started, an application with another open, failed, or submitted run, and one with no such evidence. It cancels the run, moves the job to READY_FOR_REVIEW, logs "Automatic run retried after a fix: reopened as not submitted (<evidence>): <reason>" (so stops before it no longer block), and prints `reopened <run>: cancelled as not submitted (<evidence>); the application is back to ready for review.` then `Reopened N; skipped M.` (`--dry-run`: `would reopen … (<evidence>)`, nothing written, no lock); the next pass starts a fresh automatic run through the normal pipeline (cap, fit, target, and any numeric daily cap; the reopened run's approval no longer uses a daily slot when a numeric cap is configured). With Workday account automation on (see Workday accounts), `--held` also releases the Workday account holds the account step left as `unexpected` (`releasableWorkdayHolds`, `releaseWorkdayAccountHold`): those stops happen before any run is saved (the account step runs before the walk), so no run is listed for them and the host's hold in the accounts file is what keeps the pipeline away. Each is cleared (email, password, account state, and creation time kept) with a line `released the Workday account hold on <host> (<reason>): the next pass signs in with the saved password.` (or `tries the account step again.` when no usable password is saved) and a count `Released N Workday account hold(s).`; `--dry-run` prints `would release …` and writes nothing; `--start` runs the pass when a run was retried or a hold released. Without the account settings the output is unchanged. The local `automatic-retry` suite (`pnpm test:agent:retry`) covers it with fake pages and temporary accounts files, no network.

A hard SKILL or EXPERIENCE requirement that names a resume skill passes with "Your resume lists …"; verified evidence keeps its own wording when both apply. Resume skills also count toward technology overlap and preferred coverage and are never penalized as missing. Skill names match as whole words or phrases (`mentionsSkill`), replacing a substring check that let "C" match inside "React"; squashed keys such as `nodejs` still meet spaced text such as "Node.js". General requirements that name no skill ("real-time web applications", "at least one programming language") still need the candidate's review.

A listed skill also covers its other names and the broader skill it is a kind of, one way only (`SKILL_IMPLIES` in `skill-keys.ts`): PostgreSQL covers Postgres, SQL, and relational databases; Machine Learning and ML cover each other, and QLoRA covers LoRA, fine-tuning, machine learning, and LLMs (large language models); Redis, MongoDB, and Firebase cover NoSQL; AWS and its services cover phrases such as "cloud platforms" and "cloud infrastructure" but never a bare "Cloud", so "Oracle Cloud" stays unmet; SQL never covers PostgreSQL. The reason names the term: "Your resume lists PostgreSQL (as SQL)". Both hard requirements and fit use the same table.

Degree lines for a candidate whose profile degree is a bachelor's are read word by word (`degree-reading.ts`) before the older token-overlap fallback. A line passes only when every word is understood: a run of degree levels that includes a bachelor's ("BS, MS, or PhD", "Bachelor's or Advanced degree", "Bachelor's degree or higher"), a field list that names the profile field of study or asks for a STEM, technical, technology, quantitative, or scientific field, and ordinary enrollment wording. "Information Technology" is its own field, a family word after "related" counts only when no other field is listed ("EE, ME, or a related technical field" stays a judgment), and graduation-window words are understood only when the posting's graduation constraint checks them separately. Anything else (full-time, class year, GPA, credit hours, a country, "(obtained)", a high-school diploma, enrollment after the internship, "applicable major") leaves the line for review. The graduate-only exclusion uses the same level runs, so "BS, MS, or PhD" is no longer read as graduate-only. The exclusion also reads a deterministic line left PREFERRED only for lack of any cue (confidence 0.4) when it states current graduate enrollment ("Current students pursuing a master's degree in …") and has no preference wording; a Preferred heading or "preferred" keeps it soft. "Full-time" in a degree line is understood only when the candidate's `enrolled_full_time` answer is yes; while it is unrecorded, a line that would otherwise pass says to answer "Are you a full-time student?" in candidate memory, and a no leaves the line for review rather than failing it. A B.S. and a B.A. are different degrees: a line that names only one kind ("B.S.", "Bachelor of Science", "BS/MS") and not "bachelor's" or "undergraduate" in general pauses for a candidate with the other kind (`bachelorKindMismatch`), ahead of both the word-level reader and the token-overlap fallback.

## Hybrid fit assessment

New deterministic analyses use scoring version 2: normalized technology coverage (70% when preferred capability requirements exist, otherwise 100%) and preferred skill/experience keyword coverage (30%, or 100% when no technologies exist). There is no automatic 50-point baseline, unrelated evidence-count bonus, or unspecified-work-mode bonus. Zero with no comparable extracted requirements is explicitly described as insufficient measurement. Existing version-1 results are labeled legacy until refreshed. Fit remains separate from legal, degree, graduation and other eligibility checks.

The configured `MODEL_API_*` provider automatically judges overall competitiveness from the full normalized description after discovery and during `advancePipeline`. It no longer requires extracted SKILL/EXPERIENCE rows. Inputs include approved non-archived resume entries, ALLOWED + CURRENT claims, and candidate-entered academic profile fields (school, degree, field, graduation date, GPA). Each saved course (`candidate_coursework`) is also a citable evidence item `course:<CODE>` (code upper-cased, spaces as hyphens; text: code and title, school, term, and status, with an in-progress course labelled "in progress (not yet completed)"; no grades), appended after the existing at most 80 items so courses never displace them; the prompt tells the model an in-progress course is current study, never completed coursework. Names, contacts, legal facts, credentials, browser state and student IDs are excluded; textual identifiers and credential patterns are redacted. The input also carries a non-citable `candidateContext` (`fitCandidateContext`): the candidate's application intent (`candidate_application_intent`, migration 0028; set with `pnpm fit:intent --set "<statement>"`, shown with `pnpm fit:intent`, removed with `pnpm fit:intent --clear`; redacted like other text) and their level (school, degree, field, expected graduation from the global `graduation_date` fact or else the profile, the target term from `INTERNSHIP_AGENT_TARGET_TERM`, and the school years left after it, derived from the graduation date by `termStanding`). The intent states preferences only; it is never evidence, a citation, or an application answer. Documented example statement: "CS student graduating in 2028, looking for a Summer 2027 software engineering or adjacent internship (SWE, ML, data or infra engineering). I'd rather apply to any role I'm a realistic candidate for than only sure bets. Skip roles that need experience or degrees I don't have, or that aren't really engineering." Descriptions over 60,000 characters are rejected rather than silently truncated. The candidate explicitly approved this automatic model assessment. The existing provider, rate limiter and invocation ledger use `job.semantic_fit`; page reads never call a model.

Version-2 AI responses contain a model-chosen 0-100 judgment of how reasonable a shot the application is and how well it matches the candidate's intent (the bands are unchanged: STRONG 75-100, a good shot and clearly wanted; MODERATE 40-74, a reasonable shot with real gaps or a crowded field; WEAK 0-39, a long shot or not what the candidate wants), or an INSUFFICIENT_INFORMATION rating; HIGH/MEDIUM/LOW confidence in the assessment; summary, strengths, gaps, and uncertainties. The prompt distinguishes duties and training from entry requirements and considers transferable projects/experience and academic alignment rather than keyword arithmetic. It also asks the model to weigh, from general knowledge, how selective the employer or program usually is (big tech, top quantitative firms, prominent AI labs, and well-known programs draw very large pools; mid-size companies and startups are often more reachable) against the candidate's evidence and level, never stating odds, acceptance rates, applicant counts, or other pool facts, and naming that read as uncertain. Every strength/gap quotes the full description exactly; strengths additionally cite exact approved candidate evidence. Validators check source membership, quotes, rating/score consistency, and prevent an unsupported assessment with no evidence. Citation validity does not prove semantic accuracy. Missing evidence is never a candidate fact, and eligibility verdicts, approvals, application packages, and submission state are untouched by this service.

Migration 0024 stores local assessments and input versions. Migration 0025 distinguishes version-2 failures from legacy extraction failures so they cannot block the new algorithm. Migration 0028 adds the application intent table (its triggers bump the context version) and bumps the context version once for the intent, level, and selectivity prompt (2026-11-19), so every fit scored by the earlier prompt is stale everywhere (cache, the Jobs/Review join, failure backoff) and is re-scored, at most 25 per pass; a future prompt change bumps the context version the same way. Migration 0031 adds the coursework table (its triggers bump the context version) and bumps the context version once for the course-evidence prompt sentence (2026-11-19). Changing `INTERNSHIP_AGENT_TARGET_TERM` does not by itself re-score fits. Academic/profile/resume/claim/coursework changes invalidate context; requirement and snapshot revisions also invalidate caches. Changed inputs during a call discard the response. Version-1 capability coverage caches are stale and excluded from competitiveness ranking. Jobs and Review Queue sort only by current AI scores; unassessed jobs follow assessed jobs. Keyword estimates remain secondary detail and the existing deterministic pipeline fallback when no current AI judgment exists. Automatic model failures retry after 24 hours or changed inputs; explicit Analyze fit with AI is available. A response the citation validator rejects is repaired up to twice from the named defects — every attempt passes the same strict validator — before it counts as a failure. Pipeline passes attempt at most 25 uncached, nonterminal, non-skipped postings in addition to discovery's new postings.

AI scores are **uncalibrated judgments of a reasonable shot and intent match**, not acceptance probabilities. Confidence describes certainty about fit, not hiring likelihood. Applicant competition, interview performance and hiring decisions remain unknown. Synthetic tests prove contracts and safety, not real-world accuracy. `pnpm verify:fit:model` is an explicit benchmark-tier configured-provider transport/citation smoke with fictional seed data and temporary SQLite. Human review remains necessary before claiming ranking accuracy.

## Model routing and cost

`packages/agent/src/model/` exposes a provider-neutral `complete(task, { tier })` interface. Domain packages never name a model. `packages/jobs` accepts a `RequirementClassifier` by injection — the same pattern as `GitHubClient` and `SemanticQuestionMapper` — and the orchestrator in `packages/agent` is the only place that chooses between the deterministic and model-backed implementation. With no `MODEL_API_KEY` configured, ingestion runs fully deterministically rather than failing; those rule labels never drive an automatic run, because the pipeline starts a browser run (and so auto-submit) only when every requirement row has `extraction = 'MODEL'`. With a model configured there is no rule-label fallback: `ModelRequirementClassifier` returns a model decision for every requirement line or throws `RequirementLabelsUnavailableError`, and a model answer that leaves a line unlabelled is treated the same way. It sends `reasoning_effort: "medium"` (reasoning tokens count against `max_tokens`), labels batches of 10 lines two at a time (budget 2,000 + 600 per line), splits a batch in half on a budget overrun, an unparseable or incomplete answer, or a timeout (each half keeps at least the parent's budget), retries a single line at doubled budgets up to 12,000 (at most twice), and stops after 48 calls per posting. A posting the model still cannot label is stored (snapshot, locations, pay, technologies, constraints) with no requirement rows and a `requirement_label_holds` row (migration 0027) holding the reason, plus an application event; while held it is not analyzed, prepared, or run. Each pipeline pass first retries up to 25 held postings from their stored snapshots (`src/requirement-relabel.ts`; dismissed postings are skipped), replacing the requirements and clearing the hold in one transaction and re-evaluating an existing match; each posting still held adds "AI requirement labels unavailable; will retry: <Company> — <Title>." to the pass errors. The dashboard's Analyze button retries that posting's labels first. `defaultedEnrollmentStatement` (graduate-only exclusion on defaulted PREFERRED lines) applies to rule labels only; the classifier prompt instead tells the model that a bullet stating who the role is for (current enrollment in a named degree program or level of study) is HARD unless framed as preferred. Before this change a failed classification silently kept rule labels stamped `MODEL`; `pnpm labels:hold-fallback [--profile real|demo] [--apply]` finds postings with stored rule labels or a failed classification call before their current snapshot and, with `--apply`, holds the repairable ones (DISCOVERED, ANALYZING, NOT_QUALIFIED, QUALIFIED) under the pipeline lock: no deletes, no status changes, no model calls; the next pass relabels them. Every model call in a process goes through one shared `ModelRateLimiter` per endpoint and model (`src/model/rate-limiter.ts`), set from `MODEL_REQUESTS_PER_MINUTE` and `MODEL_TOKENS_PER_MINUTE` (defaults 100 and 3,000,000, the configured contributor model's published limits). It admits calls at 90% of both limits, spaces starts evenly (about one every 0.67 s at 100 RPM) rather than bursting, and reserves each call's estimated input plus its full `max_tokens` against the token budget, settling to the provider's reported usage afterwards. A 429 or 503 pauses the whole limiter for `Retry-After` (or 2, 4, 8, 16 s); a network error ("fetch failed") and a 500 or 502 back off the same way without pausing the limiter; each is retried up to five attempts in total. A 504 and the provider's own two-minute timeout are not retried by the provider (the same request would likely time out again), and the request timeout covers the request, never the wait for a slot. A truncated (`finish_reason: "length"`), empty, unparseable, or wrongly shaped answer raises a typed error (`ModelOutputBudgetError`, `ModelInvalidOutputError`, `ModelTimeoutError` in `src/model/provider.ts`) so callers can send less work per request. Separate processes (the dashboard and `pnpm pipeline:run`) each hold their own limiter, which the 10% margin and 429 handling absorb. Discovery ingests up to `INTERNSHIP_AGENT_MODEL_CONCURRENCY` postings at once (default 32, 1-64): each posting's duplicate checks and SQLite write stay synchronous, only the model wait overlaps, and reports keep source order. Measured classification calls take about 21 s (p50) and 3,100 tokens, so the request limit binds long before the token limit. The dashboard's `dev`, `build`, and `start` scripts load the repository-root `.env` through `apps/dashboard/scripts/with-root-env.mjs` (shell variables win); Next.js alone reads only `apps/dashboard/.env*`. The browser harness launches `next dev` directly, so its runs never inherit the root model settings. One-off scripts must pass `--env-file-if-exists=.env` themselves.

A classifier receives requirement text and indices only. It never sees or returns a span, so it cannot anchor a requirement in text the posting does not contain, and an index it invents is discarded. A failed model call falls back to the deterministic reading rather than failing ingestion.

`model_invocations` records task, tier, model, optional job attribution, token counts, duration, and outcome for every call, including failures. The configured model reasons before answering, so billed output tokens substantially exceed the returned JSON; the request timeout and output budget are sized for that.

## Resumes and browser sessions

Generated resumes are built from the candidate's structured resume entries. `resume_entries` gives each experience, project, or skills group a stable identity, section, position, and archive flag; `resume_entry_revisions` stores every edit (title, role, link, location and date exactly as written, bullets or skill items, source, review status) and supersedes, never deletes, the previous revision. Entries the candidate types are approved on save. Entries transcribed from a base resume record that resume's id and checksum and stay `PENDING` until the candidate approves them; a stale revision cannot be approved. `candidates.gpa` holds the GPA as printed on the candidate's resume.

Preparation uses every active, approved entry in the candidate's order, verbatim, with no per-job tailoring. Each experience or project bullet and each skills line becomes a resume bullet, and each entry heading becomes a claim. Their `resume_entry` basis names the exact revision, and the verifier passes a line only while that revision is current, approved, unarchived, and still contains the exact text. Evidence claims still ground answers and relevance but never become resume bullets. The variant freezes the structured document (`resume_variants.document_json`) alongside a readable markdown snapshot. The document renders in the candidate's layout: centered name and linked `•` contact line; Education as school — degree | GPA (Expected Month YYYY); Professional Experience headings in small caps as organization | role with location and date right-aligned; Projects with their link; Technical Skills as `Label: items`. `@internship-agent/browser` prints it to a Letter PDF with a throwaway headless Chromium and reports the page count; an upload of the generated resume stops when it exceeds one page (that stop applies only to the generated print, never to the candidate's uploaded resume; `pnpm profile:resume` warns when an uploaded resume is not one page). Variants made before structured entries print their markdown snapshot. The application page labels each variant with what the application actually sends (browser runs record the truth; before a run, the candidate's uploaded resume for the expected profile when one is stored, otherwise the newest variant, printed with the 2029 graduation date on Handshake-internal postings, whose Quick Apply dialog instead keeps the Handshake account's resume once the candidate confirms it) and links to `/applications/<job>/variants/<variant>`, which prints that variant exactly as an upload would.

`candidate_documents` records other candidate-supplied PDFs (today only the `transcript`) the same way, under `<profile data dir>/documents/`. Nothing is read out of a transcript: no student ID, grades, or courses become facts.

`base_resumes` records candidate-supplied PDFs (channel `default` or `handshake_internal`, original name, SHA-256, size); the bytes live in `<profile data dir>/resumes/<id>.pdf` with owner-only permissions. One row per channel is current; replacements supersede, never delete. File-upload fields are routed by their label: a resume or CV field receives the resume, a transcript or academic-record field receives the stored transcript, and a cover letter or any other attachment stays empty when it is optional ("Optional upload left empty; the agent attaches only your resume and transcript.") and pauses for the candidate when it is required (text answers never fill an upload pause). An application uses the candidate's alternate (2029) profile when it is Handshake Quick Apply / Apply or its form asks for a transcript; that profile's resume, the transcript, and 2029 graduation answers travel together. A transcript field without a stored transcript stops the run before anything is filled.

A resume field receives the candidate's current uploaded resume for the run's profile, byte for byte: `default` on default-profile runs, `handshake_internal` on alternate-profile runs (Handshake Quick Apply / Apply, a form asking for a transcript, or a company pinned to the transcript profile); Workday chooses per step, switching when a step asks for a transcript. The decision records basis `base_resume`, and the run records `base_resume_id` (null when the run uploads no resume, for example a Quick Apply run that keeps the Handshake account's attachment). Nothing is printed for that upload and the generated resume's page limit does not apply. Each upload (start, continue, and submit, including auto-submit) re-checks that the file is still the channel's current upload (a replacement since the run was planned stops the run) and matches its SHA-256 (a missing or changed file stops it), then copies the bytes to `<profile data dir>/applications/<job>/uploads/<base resume id>/<original file name>` (mode 600) and uploads that copy, so the site receives the candidate's own file name. Without an upload for that profile, or with `INTERNSHIP_AGENT_RESUME_SOURCE=generated` (only that value opts out; unset or anything else sends the upload), the generated variant is used as before: the variant snapshot rendered to PDF at `<profile data dir>/applications/<job>/resume-<variant>.pdf`, or on alternate-profile runs the same variant printed with the candidate's `handshake_internal` graduation answer in place of the default one (`printResumeVariant` with a graduation override; nothing else in the frozen document changes; without that answer the run stops before anything changes), with the one-page stop. Preparation always builds the variant: the package, its verification, the review page, and the fallback rely on it. Runs planned before this rule keep their decisions: variant decisions print the variant, and a `base_resume` decision whose upload was since replaced stops.

`pnpm profile:resume --profile real|demo` lists the current uploads of both channels (label, original name, page count, size, SHA-256, stored time; a missing or changed file is flagged). `pnpm profile:resume --profile real|demo --channel default|handshake_internal --file <pdf> [--label <text>] [--dry-run]` stores a PDF with `storeBaseResume` under the pipeline lock, superseding the channel's current upload, and prints its label, page count, and SHA-256; it warns when the PDF is not one page (never blocking), skips a file whose bytes equal the current upload, and `--dry-run` prints `would store …` and writes nothing. Agents never run it against the real workspace.

Real runs open a visible Chromium window on the profile's persistent `browser-profile`, which is less likely to trip bot detection than headless; `HEADLESS=1` opts into headless. Nothing hides automation or works around a challenge: a safeguard still halts the run. The hidden CAPTCHA token field (`g-recaptcha-response`, `h-captcha-response`, `cf-turnstile-response`) and the invisible, v3, or Enterprise reCAPTCHA badge are page machinery, not questions or challenges: the browser submits normally and the site's own scoring decides. Only a challenge the candidate would see pauses the run as a safeguard: a visible reCAPTCHA checkbox or image challenge, an hCaptcha or Turnstile widget, a DataDome CAPTCHA page, or a human-verification page (`packages/browser/src/challenge.ts`, which only reads the DOM: no solving, token injection, stealth, fingerprint change, or evasion). One seen before the submit click withdraws the approval and pauses the run; one that appears after the click (`SubmissionChallenged`), or a site error instead of a confirmation (`SubmissionRefused`), fails the run without marking it submitted, and the pipeline lists it under "Held for you", not errors (all four post-submit outcomes, and the evidence kept for them, are described under Post-submit outcomes below). A generic (non-Handshake) run whose opened page has no form field follows the page's own Apply entry once before reading the form (`chooseApplyEntry` in `packages/browser/src/apply-entry.ts`, through the page's `followApplyEntry`): links and buttons in the main frame and same-host frames (iCIMS draws the job in a same-host iframe) are tagged and ranked by site (the same host, then the same company domain, then a known ATS host such as greenhouse.io, icims.com, or jobvite.com; any other site, including job aggregators, is never followed), and qualify by an Apply text ("Apply", "Apply Now", "Apply for this job online", "Start your application"…), iCIMS's `iCIMS_ApplyOnlineButton` or `?mode=apply` link, or Jobvite's `/apply` link; anything naming LinkedIn, Indeed, another site, sharing, referral, e-mail, "later", saving, or signing in ("Apply with LinkedIn", "Apply Later") is never used. Anchors are opened by their address, buttons clicked by their tag; a page with no such entry keeps the "No application form was found" stop. The run saves the address it reached, so continuing and submitting reopen the form itself, never the posting page. Then, on every run (automatic or candidate-started), `applicationWallReason` stops a page the agent never fills for the candidate before anything is typed or a run is saved: iCIMS's email-first account step (an `*.icims.com` address with a `/login` path: "iCIMS needs an account at <host> before its application form, and the agent does not create iCIMS accounts…") and Jobvite's data-consent step (a jobvite.com page saying "Data Consent"); an automatic run is held with that reason, a candidate-started one ends with it, unless the run's settings take the step (see Jobvite data consent and iCIMS accounts below). The generic password-field stop stays the account wall for automatic runs elsewhere. Generic form reading takes labels from aria-labelledby first; an upload labelled only "Attach" takes its upload group's label ("Resume/CV", "Cover Letter"); each field is located by its own id before its label, so two "Attach" uploads never hit the same input; react-select lists (Greenhouse's new boards) are one select whose options are read by opening the list and pressing Escape (nothing is saved), and their hidden required inputs are not controls; a fieldset of checkboxes, or checkboxes sharing a name, is one question answered with one option (a "How did you hear about us?" group from the saved `how_heard` rule); radios sharing a name are one choice question (its label from the fieldset legend, the radiogroup's label, or the question text near the first radio; its options from each radio's label), answered by checking the radio whose label equals the chosen option, and a known answer is never typed into a radio, checkbox, list, or upload (the planner pauses with "… is a choice"; the executor refuses with "it is a choice, not a text box"); `aria-required` and a trailing required marker mark required fields. Label text skips nested controls, live regions, status, listbox, and option widgets, and hidden elements, so Lever's "Current location ✱No location found…Loading" reads "Current location"; a label that wraps the whole question uses its own label element (Lever's `.application-label`); a control with no label of its own (Ashby's "Start typing..." box, Lever's custom questions) takes the question text near it (the closest legend, label, heading, or label/question/title element, or an element whose class holds "FormLabel" (case-sensitive: Dover's sibling `styles__FormLabel-…` question div), in up to six ancestors that hold no other question), with placeholder and name as the last resort. An option's own label (a label holding exactly one radio or checkbox, such as MUI's "Yes" option) and text inside an aria-hidden element are never a question's label. An upload with no label of its own looks for a nearby label (FormLabel included) in up to five ancestors and stops at the first that holds another question's control, so Dover's Resume drop zone reads "Resume", never a neighbouring radio's "Yes". A drop zone whose `role="button"` box says "autofill" (Dover's "Autofill from resume") parses a resume into the form and is not a question, like Ashby's. Every label source drops invisible characters (zero-width space and joiners, direction marks, soft hyphen, variation selectors, the byte-order mark: `INVISIBLE_CHARACTERS` in `form-recognition.ts`, copied into the in-page collector), so Dover's notched-outline legend that holds only U+200B is skipped like an empty one; a source that is a bare UUID is empty, and a name holding a UUID (Dover's custom questions) never labels a control: such a control takes its FormLabel question text, and with no other source it is "Unlabeled … control N". Buttons, button and reset inputs, and controls with a button, link, menu item, or tab role are never fields, an unknown-kind control labelled only with an action word ("Discard", "Back", "Next", "Submit"…) is dropped, and text inside a button or link (Oracle JET's `oj-button-label`) never labels a control. Type-ahead fields (a combobox or `aria-autocomplete` list input, a datalist, Lever's `location-input`, a "Start typing..." box, or a react-select list with no options until something is typed, such as Greenhouse's "Location (City)") are filled by typing the saved value, waiting up to 6 s for suggestions (the input's `aria-controls` listbox, react-select's options, Lever's `.dropdown-results`, or nearby options), and clicking the one that equals the value, else the only one with the same words (punctuation, case, accents, and of/the/at/and/in ignored: "University of California, Davis" takes "University of California - Davis"; two such suggestions are never guessed between), else the only one starting with it, or for "City, Region" the only "City, …" suggestion naming the region, where a US state's code and name stand for each other ("Springfield, IL" takes "Springfield, Illinois, United States"; `matchSuggestion`, `packages/browser/src/ats/us-states.ts`); a "City, Region" value with no match is typed again as the city alone and still matched against the whole value; with no such suggestion the typed text is cleared, its list closed, and the field left without focus, and the field is not guessed. Every list choice first closes any react-select menu left open (Escape, blur, up to 1 s): an open menu is absolutely positioned and covers the fields below it, which is how a failed School search once left Degree, Discipline, and the start month unfillable on real boards. Greenhouse's School, Degree, and Discipline lists (`school--N`, `degree--N`, `discipline--N`) are async catalogs (the school catalog spells campuses "System - Campus", "University of California - Berkeley"); their options get up to 5 s to load, and School and Discipline are type-aheads too: they search their catalogs as you type, so the first page shown on opening is never the whole list. A short Greenhouse question label with no "?" (at most 60 characters) takes its `<id>-description` text when that is a question of at most 240 characters ("HISTORY WITH IRONVALE: Have you previously applied to a position at Ironvale?"). A control with neither id nor name (Ashby's location box) is tagged `data-ia-control="ia-control-<n>"`, a tag that stays the same across recognitions, and is found again by it. On Ashby a question title's `_required` class marks the question required, a Yes/No button pair over a hidden checkbox is one radio question answered by clicking the named button (kept only when it shows pressed), a fieldset's question title (a label for none of its radios) labels its radio group, and location suggestions are read from `ashby-application-form-input-autocomplete-popup-result` rows (that class comes from Ashby's bundle; the row structure is assumed). An education block is answered from the profile only: School (the profile school typed into a searched list, its full name for "UC …", or from a native list the option with exactly its words, else the one option naming only its campus: "Springfield" for "University of Example, Springfield", never "Other"; "Which university are you currently attending?" and similar phrasings count as School), Degree (`chooseDegreeOption`: the same bachelor's kind or a general "Bachelor's", curly apostrophes read as plain ones, never a B.S. for a B.A.), Discipline (the field of study), Start date month and year (the profile's education start month), and End date month and year (the run profile's graduation date: on the default profile the global graduation answer, else the profile's date; on the transcript profile only its 2029 answer, never the default date); a value that is missing or matches no option pauses when required. The date fields are recognized by Greenhouse's education ids (`start-month--N`, `start-year--N`, `end-month--N`, `end-year--N`) as well as their labels: Greenhouse's employment block repeats the "Start date month" labels under `start-date-month--N` and the like and is never filled from education data (optional: left empty; required: a pause). A state-of-residence question ("State", "What state do you currently reside in?", "State of residence") takes the profile's address region, matched to an option by the same text or a US state's other form ("IL" picks "Illinois", exactly one); a distance question such as "within 50 miles of …" is never answered from it. Country lists match the profile country across the United States' spellings ("US", "USA", "United States of America") and a trailing dialing code (exactly one match), and Greenhouse's phone-country list, which then shows only "+1", counts as having kept "United States +1". A preferred-name field takes the profile's preferred name only; with none an optional field stays empty and a required one pauses (never the legal name). A field the page will not take (no matching suggestion, an option that is not there, a choice that is not a text box, or a 10-second field timeout) becomes a pause on that field ("The agent could not fill "<label>": <reason>. Answer it here, or fill it in the browser."), never a raw Playwright error that stops the run; on the submit path it withdraws the approval and holds the run (`SubmissionHeld`) before any click, and on Workday it pauses the walk on that step. A checkbox asking consent to keep or process the candidate's data ("… has my consent to retain my data … for up to 3 years") is never ticked automatically: it always pauses with "consent checkbox: needs your OK", even when memory says yes. Connect Handshake opens the same profile visibly on Handshake's login page; the candidate signs in by hand (CalNet, Duo) and closes the window; the agent reads only page URLs, never closes the window early (only after a 10-minute timeout), and records the status of the last Handshake page seen. Closing the last tab counts as closing the window, since macOS keeps Chromium running without windows. `browser_sessions` keeps only the last status (`connected`, `signed_out`, `unknown`), a short detail, and a timestamp. Handshake Quick Apply / Apply runs happen inside Handshake's "Apply to …" dialog: each run step clicks the page's "Quick apply" button and then reads, fills, and submits only inside that dialog (a Handshake-internal posting without Quick apply stops the run). A resume Handshake already attached comes from the candidate's Handshake account; the agent never removes or replaces it. The run records it as a `keep` decision and pauses with "Is it your current resume?": only a yes answers it (anything else says to update the resume on Handshake and start a new run), so submission cannot be approved until the candidate confirms. Continuing and submitting re-read the dialog, and the attachments must be exactly the ones confirmed. The submit click is a real (trusted) mouse click on the chosen control, which prefers a button that says submit and never counts a "Quick apply" opener, a cancel control, or a hidden or disabled control. The page then stays open for up to 30 seconds while a confirmation is awaited; a confirmation counts only if its phrase appears more often than before the click, or a site's own success container appears that was not there before the click (Ashby's `.ashby-application-form-success-container`, a role=status region whose message may be the employer's own wording). Otherwise the run fails with a message that the click happened (and whether the dialog closed) and asks the candidate to check the site before retrying, unless the site marked fields invalid (the run is then paused for answers; see Post-submit outcomes). A new run may start after a failed or cancelled run as long as no run for that job was ever submitted. Every run step checks the landing URL first: a Handshake sign-in page stops the run before anything is filled or any status changes. The sign-in path list is partly observed (a signed-out `/login` redirects to `/access`) and partly a best-effort reading of Handshake's URLs; it has not been checked against a signed-in account. Whether automated use of a Handshake account fits Handshake's terms is the candidate's decision; submission stays human-approved.

**Jobvite data consent and iCIMS accounts.** With the standing data-consent setting on (`INTERNSHIP_AGENT_ACCEPT_DATA_CONSENT=1`), Jobvite's Data Consent step is taken on any run, at start, continue, and submit (`passJobviteConsent`, `packages/browser/src/ats/jobvite-consent.ts`; `acceptJobviteConsentStep`, `packages/agent/src/standing-consent.ts`): the "Location of Residence and Language" option naming the profile country is chosen (`chooseResidenceOption`: any spelling of the United States for a US profile, never a "Non-US" option, English kept when several match), the step's one Accept control is clicked, and the timeline logs "Accepted data consent: '<the policy text shown>' (Jobvite Data Consent at <host>; residence "<option>")"; then the form behind it is read and filled as usual. No saved country, no single matching option (nothing is clicked), a CAPTCHA, or a step still shown after Accept stops the run with a plain reason; the setting off keeps the stop above. iCIMS accounts are opt-in (`INTERNSHIP_AGENT_ICIMS_ACCOUNTS=1` with `INTERNSHIP_AGENT_AUTO_APPLY=1`, manual checklist mode off, and an account email, `INTERNSHIP_AGENT_ACCOUNT_EMAIL` else `INTERNSHIP_AGENT_WORKDAY_ACCOUNT_EMAIL`, equal to the profile email; `icimsAccountSettings`) and apply to automatic runs only. At iCIMS's email-first step (`ensureIcimsAccount`, `packages/agent/src/icims-account-service.ts`; screens read by `packages/browser/src/ats/icims-account.ts` in iCIMS's same-host content frame (`icims_content_iframe`, `?in_iframe=1`) when the career site draws one, else in the page; CAPTCHA detection covers both) the agent enters the account email, ticks the step's data-consent box only under the data-consent setting (logged "Accepted data consent: '<text>' (iCIMS email step at <host>)"; a marketing box stays unchecked; a required box the setting does not accept holds as `consent-setting`, released once the setting is on, or `consent-unknown`), and then either creates the profile (a random 16-character password per host saved first in the owner-only `icims-accounts.json`, `INTERNSHIP_AGENT_ICIMS_ACCOUNTS_FILE`, default `~/.config/internship-agent/<profile>/icims-accounts.json`, required when `INTERNSHIP_AGENT_DATA_DIR` is set, marked `pending` just before the submit; the saved legal first and last name, the email, and the phone when saved; any other required field holds as `profile` before anything is typed) or signs in with the saved password. An existing account with no saved password holds ("an iCIMS account exists for your email at <host> but no password is saved"); a refused or wrong saved password, a lockout, "already exists" after a create, and no answer to a create hold and are never retried; a CAPTCHA (hCaptcha included) holds and is never solved; an emailed verification link is read from the read-only Gmail mailbox (`findIcimsVerificationLink`: https, the tenant host or another `*.icims.com` host, an activation path) and opened in a new tab, then the agent signs in; an emailed code holds. Every hold (`IcimsAccountHeld`) is stored with the host's entry, reported by the pipeline under `waiting` (reason `icims-account`, site key `icims:<host>`), logged "Automatic browser run waiting: …", saves `icims-account` evidence for the job, and keeps later passes from opening a browser until it allows (verification holds retry after 1 hour, doubling up to 24 hours). The agent does not walk iCIMS's multi-page application yet: once the application shows, the run stops ("… but it does not fill iCIMS's multi-page application yet …"), saves `icims-application` evidence (screenshot and redacted text, for a follow-up adapter), and saves no run; iCIMS and Jobvite stay recognized kinds the candidate approves. `pnpm icims:account [--profile real|demo]` lists hosts and their state; `--site <host or URL>` prints that host's email and password; `--site <host> --clear-hold` clears its hold (the password stays) so the next pass retries it.

Handshake's observed post-submission job page shows "Applied on <date>". The confirmation reader recognizes that phrase only when it newly appears after the submit click, using the same before-and-after rule as other confirmations. Each phrase is counted on its own, and the longer ones ("Thank you for applying", "We've received your application", "We have received your application") are separate phrases from a bare "thank you", so a job description that already says "Thank you for your interest" cannot hide a later "Thank you for applying". A site's own confirmation address also counts when the page before the click was not one: Greenhouse's `/confirmation` path or `?confirmation` parameter on `job-boards.greenhouse.io`, `boards.greenhouse.io`, and their `.eu.` hosts, and Lever's `/thanks` path on `jobs.lever.co` and `jobs.eu.lever.co` (`isConfirmationUrl`, `readNewConfirmationUrl` in `packages/browser/src/submission-outcome.ts`; the URL rules come from public knowledge and were not checked against live pages). A page read that fails during the navigation never ends the wait.

**Post-submit outcomes.** `submitAndConfirm` sorts every submit click into one of five outcomes, read deterministically from the page: (a) **confirmed** (a new confirmation phrase, the site's success container, or a new confirmation URL): the run is submitted; (b) **field errors**: at the 30-second deadline the site marks fields invalid that were not invalid before the click (`aria-invalid="true"` controls and shown error elements: Greenhouse's `<id>-error` and `.helper-text--error`, error-classed elements in Ashby's and Lever's field containers; the selectors are generic and unverified live, so a miss only makes the outcome unknown) and still shows the submit control, so nothing was sent: `SubmissionNeedsInput` makes the run `paused-needs-input` with the approval withdrawn and one open pause per field carrying the site's error text ("School: This field is required."), a field the form recognition cannot find (by id, else a unique label) becoming a `site-error-<n>` safeguard; the pipeline lists it under "Held for you", its message names only the field count, and it is eligible for `pnpm pipeline:retry`; (c) **refused or challenged**: a site error instead of a confirmation (`SubmissionRefused`) or a CAPTCHA that appears after the click (`SubmissionChallenged`) fails the run without marking it submitted, the approval kept, and the pipeline lists it under "Held for you", not errors; (d) **unknown**: nothing recognized (`SubmissionUnconfirmed`, with the same two messages as before) fails the run closed and is listed under errors; (e) **verification code requested** (`verification-code`): after the click, new security-code inputs appear (Greenhouse's `#security-input-<n>` boxes, `autocomplete="one-time-code"`, or a field named or labelled for a security or verification code; none before the click) with text about a code sent by email. On a Greenhouse board the agent polls the candidate's mailbox read-only (`greenhouseSecurityCodeLookup` in `packages/agent/src/greenhouse-security-code.ts`, through the Gmail `VerificationMailbox` the Workday verification uses, every 10 s for up to 3 minutes) for mail from greenhouse-mail.io or greenhouse.io (dot-bounded) whose subject says "security code" and names the posting's company (`mentionsCompany`), received from 30 s before the click on; exactly one distinct 6–8 character token after a "code …:" anchor (in the text or the HTML read as text) is typed in (one character per box), the step's own submit (the first enabled submit, verify, confirm, or continue control after the boxes) is clicked, and the confirmation wait restarts. None, several, no mailbox (`INTERNSHIP_AGENT_GMAIL_*` unset), an unreadable mailbox, a field that does not take the code (read back after typing), or a non-Greenhouse page hold the run (`SubmissionCodeNotFound`): `paused-needs-input` with the approval withdrawn and a `site-security-code` safeguard pause ("Greenhouse emailed a security code; it was not found …", naming `pnpm pipeline:retry --run <ref>`), listed under "Held for you" and retryable; a step still shown after the code was entered fails closed (`SubmissionUnconfirmed`, verification-code evidence). The code is never logged, stored, sent to a model, or put in an event, notice, error, or evidence: every text read after it was typed is scrubbed to "[code]" and no screenshot is taken. Unverified boundary: the step's markup and the email's wording come from third-party descriptions of Greenhouse's new boards (open-source automation projects), not a capture; a different real markup falls back to unknown (fail closed). Only (b) and (e)'s holds are retry-eligible; (c) and (d) keep their approval, so `pnpm pipeline:retry` refuses them (except the `--reopen-unsubmitted` override with evidence, under Retrying held automatic runs), and nothing is ever retried automatically.

**Post-submit evidence.** On every outcome except a confirmation, `submitBrowserRun` keeps what the page showed in `<profile data dir>/applications/<job>/submit-evidence/<time>-<run>/` (`packages/agent/src/submit-evidence.ts`; directories mode 700): `screenshot.png` (a full-page screenshot; none once an emailed security code was typed, since it could show the code) and `evidence.json` (mode 600: the outcome, `verification-code` among them, the final URL with its query and fragment removed, the invalid fields with their labels and the site's error texts, the site's error text, the challenge, and the visible text redacted line by line like the pipeline's notices, so emails, URL queries, and long digit runs are removed, capped at 20,000 characters). The run's timeline logs "Post-submit evidence saved (<outcome>): applications/<job>/submit-evidence/<folder>; view it with pnpm run:evidence --run <ref>." (a path relative to the data directory only); a failure to save logs "Post-submit evidence not saved." and never changes the outcome. The evidence stays local: it is never sent to Discord or a model. `pnpm run:evidence --run <id or 8-character prefix> [--all] [--profile real|demo]` (`packages/agent/scripts/run-evidence.ts`, read only) prints the newest capture (all of them with `--all`): its outcome, URL, invalid fields, site error text, challenge, screenshot path, and redacted text. Workday stops are saved the same way while the page is still open (`saveWorkdayEvidenceQuietly`, `captureWorkdayEvidence`): outcome `workday-errors` when Workday would not save a step (the run's folder; Workday's errors as invalid fields with their labels and the rest as the site error text; detail "Workday could not save <step>."), and outcome `workday-account` when the account step held the host. No run exists yet for an account-step stop, so its folder is the job's, `<time>-workday-account`, with `runId` null, the hold reason as `detail`, and the account email and the host's saved email and password replaced by "[redacted]" in every text (the screenshot may still show the typed email; it stays local). The timeline logs "Workday evidence saved (<outcome>): <path>; view it with pnpm run:evidence --run <ref>." or "… --job <ref>."; a failure logs "Workday evidence not saved.". `pnpm run:evidence --job <id or 8-character prefix> [--all]` prints a job's evidence, its runs' and its account-step stops', each with a `Run:` line (`Run: none (the account step stopped before a run was saved)`); both modes print the `Detail:` line when one is stored. Files written before this field read with `detail: null`. The local `submit-evidence` suite (`pnpm test:agent:evidence`) covers the files and the command.

**Application records.** After a confirmed submission (the candidate's approval or the auto-submit policy; both go through `submitBrowserRun`), `packages/agent/src/application-record.ts` writes `<profile data dir>/applications/<job>/application-record.pdf` atomically with mode 600. It holds the company, role, posting URL, application URL, site type, submission time, who approved it (the candidate, or the auto-submit policy with its basis text; never both), the profile used (default, or the transcript alternate) with that profile's current graduation answer and the graduation date answered on the form, every form field as submitted (label, value, source; uploads named, fields left blank listed), each uploaded file with its SHA-256, the confirmation text, and the posting snapshot (first 100,000 characters). The profile shown is the run's recorded `applicationProfile` (default or transcript, as the company's graduation-profile lock chose it; migration 0029), read through `profileOfRun`, so runs recorded before that migration fall back to their decisions; its graduation date is the matching saved answer. The record is rendered with `renderHtmlToPdf`; the attached resume and transcript are appended as pages with pdf-lib 1.17.1 (`appendPdfPages`) when they are readable and match the recorded checksum, otherwise referenced by name and SHA-256. A printed resume variant's checksum is of the file on disk when the record was made; a transcript moved to a `documents.removed-*` folder is still found. Form labels are captured at submission into `submitted-field-labels.json` (mode 600) so regenerated records keep them; records for runs submitted before this change reconstruct labels from each answer's source and mark them in italics. Writing a record is best-effort and never changes the submission; the timeline logs "Application record saved locally." or "Application record not saved; run pnpm application:record --job <id>." (never a path or an error). Manual check-offs get no record at check-off. `pnpm application:record [--profile real|demo] [--job <id>] [--all-submitted]` (re)writes records for submitted applications under the pipeline lock: no flags writes only missing records; manual check-offs get an honest record saying the agent did not fill the form. It is a manifest benchmark entry that no gate runs. The Discord pass notice only says "Record saved locally." under a sent item; it never reads, attaches, or sends the record.

## Candidate memory policy

The fact catalog includes relocation willingness, work authorization, sponsorship need, availability date, graduation date, and full-time enrollment, plus how the candidate heard about a job (`how_heard`, text), previous employment at the company (`previously_worked_here`, company-scoped Yes), 18 or older (`age_18_or_older`), pronouns (`pronouns`, text, sensitive), relatives at the company (`relatives_at_company`, company-scoped Yes; "relatives", "family members", "immediate family", or "related to" working at the company, but never a question about family who use, buy, sell, or practice health care with its products, customers, vendors, or suppliers), the latest internship end date (`available_end_date`), openness to on-site and hybrid work (`work_arrangement`; also "required to be in the <city> office. Are you ok with this requirement?", but never "willing and able to work from this location", which depends on where the candidate lives or would relocate and pauses), relevant coursework (`relevant_coursework`, text, global; built from `candidate_coursework`, never stored as a fact), and the protected voluntary self-identification keys `eeo_gender`, `eeo_race_ethnicity`, `eeo_veteran_status`, and `eeo_disability_status` (each limited to its listed categories). Each definition declares its value schema, allowed scope, sensitivity, allowed source, and reuse policy. The `text` value type was added by migration 0030, which rebuilds `candidate_facts` keeping every row, both indexes, and the AI-fit context triggers from 0024.

Deterministic mapping handles reviewed paraphrase families and returns a confidence and match method. It does not interpret an answer or create a fact. Unknown and ambiguous questions pause; a question asking for both a start and an end date, or a bare "End Date" box, is not mapped. Per-application attestation questions are flagged for direct handling; the browser planner signs only the whitelisted kinds below, and only under the candidate's setting. Work authorization also maps "legally eligible to work" and "legally able/permitted to work", except when the question names government, export-control, citizenship, clearance, contract, or project wording.

**Standing consent and attestations.** Two explicit candidate settings (2026-11-20), read by `standingConsentSettings` (`packages/domain/src/standing-consent.ts`) and both off in manual checklist mode: `INTERNSHIP_AGENT_ACCEPT_DATA_CONSENT=1` accepts data-processing, data-retention, and privacy-policy consent that is a condition of applying; `INTERNSHIP_AGENT_SIGN_ATTESTATIONS=1` signs accuracy certifications ("I certify that the information … is true", "false statements may result in …"), electronic signatures, acknowledgments (at-will employment, a privacy or applicant notice read, a temporary internship, an equal-opportunity statement), and background-check, consumer-report, drug-test, reference-check, employment-verification, and arbitration authorizations. The classifier (`classifyStandingStatement`, `standingStatementDecision`) is a deterministic whitelist of phrasings per group. Statements of fact about the candidate veto acceptance first and fall through to the usual rules (a saved fact or question-memory answer fills them, else they pause): citizenship, U.S. person, export control and ITAR, government or DoD eligibility and clearance, FDA/OIG debarment and sanctions, conflicts of interest, criminal-history assertions (an authorization that only mentions criminal history is not one), prior employment, non-compete and restrictive covenants, relatives, work authorization and sponsorship, age (including "18 or older"), enrolment and degree, demographic self-identification (a demographic veto for self-identification phrasing: "I identify as…", "I am a veteran/female/…", "my gender/race…", "self-identify"), and, as a separate first-person-fact veto, any other "I am …" assertion ("I am able to work onsite…") except certification verbs ("the information I am providing/submitting…"), so an ordinary accuracy certification is signed; `factGroupsOf` names every fact group a statement matches. Marketing, newsletter, job-alert, talent-community, and text-message opt-ins are never accepted by these settings (texts follow the text-message rule below): an optional one stays unchecked and a required one pauses ("marketing opt-in: needs your OK"). A statement spanning both kinds needs both settings, and a label recognition clipped ("…") is never accepted. `standingFieldDecision` (`packages/browser/src/standing-fields.ts`) runs in `planAutofill` before the sensitive-role rule (a sensitive list or radio set never reaches it; a single checkbox may): a single checkbox is checked, a consent list or radio set takes its one affirmative option ("Yes", "I agree"), a text box whose label names an electronic signature takes the saved legal first and last name (else the full name; with neither it pauses), and a "Date" box beside a signature takes today's local date in the label's format (MM/DD/YYYY, DD/MM/YYYY, YYYY-MM-DD, MM-DD-YYYY; a date input takes YYYY-MM-DD; else MM/DD/YYYY). Without the attestation setting a signature box always pauses ("electronic signature: needs your OK"); without the data-consent setting a data-retention box pauses as before (`CONSENT_QUESTION`). Each decision records basis `standing_consent` (setting, group, the label as read), and each applied one is logged on the timeline with the exact text (`logStandingAcceptances`, `packages/agent/src/standing-consent.ts`): "Accepted data consent: '<text>'", "Accepted attestation: '<text>'", "Accepted data consent and attestation: '<text>'", "Signed attestation: '<label>' — signed as <legal name>", "Dated the signature: '<label>' as <date>". The legal name stays in local SQLite (events and run decisions) and is never written to console output, errors, reports, or notices. These decisions do not block the auto-submit policy (the candidate's opt-in, 2026-11-20: `autoSubmitBlockers` does not count them); its approval event adds "consent and attestation statements were accepted under your standing settings". With either setting on, a marketing opt-in asked as a Yes/No list or radio set takes its one "No" (declined, even when the label was clipped); a statement about the application itself ("text messages about your application status") is not declined; texts follow the text-message rule below.

**Text-message consent.** The candidate's rule (2026-11-20, verbatim: "Texts yes about my application status") is applied deterministically by `textMessageConsentDecision` (`packages/browser/src/standing-fields.ts`) in `planAutofill`, before the standing settings and only for non-sensitive fields, whatever the settings. `textMessageTopic` (`packages/domain/src/standing-consent.ts`) reads a consent question about texts (SMS, text messages, WhatsApp) from its label and options together: texts only about this application (its status, the hiring process, interviews) take the Yes option (a single box is checked); texts only about marketing, job alerts, other openings, newsletters, events, or a talent community take the No option (an optional box stays unchecked, a required one pauses as a marketing opt-in); a question that mixes the two, names another channel (WhatsApp, calls, email), names no topic, or whose label was clipped pauses ("text messages: …") with its label. Marketing texts are never accepted. The decision has no basis; its reason names the rule. Ashby draws its text-message consent (`communicationConsent`; `smsConsent` and `whatsAppConsent` when both channels are asked) inside the phone field's entry, in `.ashby-application-form-texting-consent-description`: the radios take the consent body's first paragraph as their label (a channel heading such as "WhatsApp" in front), never the phone's title or the radio name, and do not inherit the phone title's `_required`. A fieldset checkbox group with no legend takes its question-title label (Ashby's checkbox groups). Choosing an Ashby consent radio is saved by Ashby at once, before the submit.

Protected self-identification answers are written only by `pnpm profile:facts`. The mapper still blocks protected questions, and `resolveCandidateQuestion` and `answerCandidateQuestion` refuse protected keys, so a pause answer or the profile page never stores one. Browser runs fill them only into EEO-role select or radio fields whose label names exactly one category (gender; Hispanic/Latino yes/no; race or ethnicity; veteran; disability), that offer a decline option, and where exactly one option matches (`matchSelfIdentificationOption`, packages/browser `src/ats/self-identification.ts`, read through `savedSelfIdentification`, packages/agent `src/saved-answers.ts`). Pronoun, orientation, transgender, sex-assigned-at-birth, accommodation, and open prompts never use them, nor do free-text fields or checkbox groups (Workday's CC-305 checkboxes); otherwise the field pauses as before and an in-session answer is used for that run only. The values never enter model inputs (voice drafting and AI fit read no facts), logs, Discord notices, or reports, and the profile page shows them only as "Saved"; the run's decisions in local SQLite record the chosen option. A filled EEO question is a fill, not a pause, so it does not block auto-submit (candidate request 2026-11-19). The "How would you describe your …" lead-in is not an open prompt, and "racial/ethnic" labels are EEO questions; a "mark all that apply" list takes the one matching option.

`pnpm profile:facts --profile real|demo [--set-file <facts.json>] [--dry-run]` writes the candidate's explicitly given answers. The file is `{ "facts": [{ "key": "<fact key>", "scope": <{ "kind": "global" } (the default) | { "kind": "country", "code": "US" } | { "kind": "company", "name": "<employer>" }>, "value": <true | false | "text" | "YYYY-MM-DD">, "note": "<optional provenance>" }], "revoke": [{ "key": "<fact key>", "scope": { ... } }] }`; a protected value is one of its listed categories, for example `"eeo_gender": "<one of: male | female | non_binary>"`. Everything is validated before anything is written. Facts are saved with source `user` and source detail kind `profile` carrying the note; unchanged values are skipped, and a country relocation answer supersedes the current global one. It prints `set|unchanged|superseded|revoked <key> [<scope>]: <value>` with protected values shown as `set`, never echoed, even in errors; `--dry-run` prints `would …` and writes nothing, and without `--set-file` it lists the current facts the same way. Any fact write bumps the AI-fit context version (the 0024 triggers), so cached AI fits become stale and are analyzed again.

Relevant coursework: the mapper maps relevant-coursework and courses-taken questions ("Relevant coursework", "Which courses have you taken?", "Courses taken") to `relevant_coursework`, after every other key, and never GPA, grade, transcript, credit, online-course, certification, or training questions. `resolveCandidateQuestion` builds its answer from `candidate_coursework` (`courseworkAnswerFact`, packages/agent `src/coursework.ts`): completed courses first, then in-progress ones, each group in the stored order, as `Title (CODE)` or `Title (CODE, in progress)`, joined by "; "; with no saved courses the question needs input. The answer is never stored in `candidate_facts`: `saveCandidateFact` refuses the key, a `pnpm profile:facts` file cannot name it, and a pause or memory answer is used once. Browser runs fill it only into free-text fields; a select or radio field asking for coursework pauses.

`pnpm profile:coursework --profile real|demo [--list | --set-file <coursework.json> [--dry-run]]` saves the candidate's relevant courses, entered by the candidate from their own transcript (the transcript file is never read). The file is `{ "school": "<school>", "courses": [{ "code": "<DEPT 101>", "title": "<course title>", "term": "<Fall 2025>", "status": "completed | in_progress" }] }`. The whole file is validated before the database is opened: strict keys (so a grade or any other extra key is rejected, with its path), the two statuses, at most 40 courses, no duplicate codes (compared as evidence IDs, so `CS 61B`, `cs 61b`, and `CS-61B` collide), no runs of 8 or more digits (an ID-like number), and whitespace trimmed and collapsed. The set is replaced in one transaction under the workspace's pipeline lock (a context bump mid-pass would make in-flight fit saves fail); an identical set writes nothing and prints `unchanged: <n> courses (<c> completed, <p> in progress)`. Otherwise it prints `school: …`, `added|changed <code>: <title> (<term>, <status>)`, `removed <code>: <title>`, or `reordered courses`, then `saved <summary>` (or `cleared all courses` for an empty list) and `answer: <the coursework answer>`; `--dry-run` prefixes each line with `would ` and writes nothing, and `--list` (or no flag) shows the saved courses as `<code> | <title> | <term> | <status>` and the answer.

An optional future classifier may implement the mapper interface, but no vendor SDK or external call belongs in the default path.

Question memory (migration 0032, `candidate_question_answers`; `packages/db/src/question-answer-repository.ts`) keeps the candidate's own answers to questions outside the fact catalog. Its key is the question label normalized by `normalizeQuestionText` (`packages/domain/src/question-answer-memory.ts`): NFKD with accents removed, lower case, a trailing `*`, `(optional)`, `(required)`, or `required` dropped, `+` and `#` spelled out so C++ and C# stay apart from C, other punctuation removed, whitespace collapsed; keys match exactly, never fuzzily. Free text is stored verbatim (at most 200 characters); a select, radio, or checkbox answer stores the chosen option and is reused only where the new field offers exactly one option with the same normalized text, otherwise the field pauses; a checkbox group is answered the same way, and a type-ahead (including a react-select list with no options until typed into) takes the saved answer typed into its suggestions. Field resolution reads catalog facts first, then question memory (only for questions the catalog does not map), then pauses; a reused answer's decision has basis `question_answer`. An answer is saved only when the candidate answers a held run's question with remember on (`answerRunPause`, used by `pnpm run:answer` and the run panel), and never for questions naming the posting's company, why/interest/motivation questions, other employer- or role-specific questions (here, this company or role, salary, referral), questions the mapper blocks (protected or attestation) or finds ambiguous, sensitive fields (the EEO role and topics such as birth date, citizenship, criminal history, health), contact details, coursework and course questions (relevant coursework comes only from `pnpm profile:coursework`), acknowledgements and consents, open-ended or essay questions (`isDraftableQuestion`, textareas, voice-draft pauses, answers over 200 characters), uploads, safeguards, and Workday error reports. Those are used for that run only, and the application timeline records `Answer to "<label>" used for this run only: <reason>.`, never the answer. A saved answer is never reused on a question that names the posting's company or meets any of those rules. Saving a question again supersedes the old answer; an identical answer is left as is. `pnpm profile:answers [--profile real|demo] [--revoke <id or 8-character prefix>]` lists the saved answers and revokes one. Question memory never feeds the AI fit or voice drafting and is never sent to a model. Answering a sensitive, protected, attestation, or ambiguous pause now records the answer for that run only instead of refusing it, and `answerRunPause` reports `remembered` only when something was stored. On continue (`answeredPauseDecision`, shared with Workday's answers), an answered list, radio, checkbox-group, or type-ahead pause is chosen, never typed; a single checkbox is checked for yes and left for no; a number box takes only a number; and an answer that fits no option of the field the page now shows reopens the pause.

## Local data and privacy

The demo database stays at `data/internship-agent.sqlite`; the real database is `data/profiles/real/internship-agent.sqlite`. `INTERNSHIP_AGENT_DATA_DIR` may point to another local parent directory. The development seed and CLI default database remain demo-only. Browser-run files, base resumes, rendered resume PDFs, and the persistent browser profile use each profile's corresponding data directory. Tests and browser verification override the parent directory with disposable temporary data and verify cleanup.

Only fictional seed records are checked into source. The real profile starts empty and is populated only from explicit candidate input. Logs and harness reports must not include fact values marked sensitive or protected. Workday and iCIMS passwords the agent creates live only in the owner-only accounts files outside the data directory, never in SQLite, logs, reports, timelines, or model prompts. The legal name typed as an electronic signature stays in local SQLite only (events and run decisions).

## Verification

`testing-harness/manifest.mjs` is the suite inventory. `agent:doctor` validates commands and prerequisites. `agent:verify` maps changed paths to features. `agent:finish` is the final gate.

Feature labels include `foundation`, `profile`, `remember`, `database`, `dashboard`, `github`, `evidence`, `jobs`, `ingestion`, `discovery`, `matching`, `writing`, `verification`, `applications`, `outcomes`, `browser`, and `agent-workflow`. The `profile` gate covers separate real/demo SQLite files; a browser switch that checks candidate, job, evidence, and base-resume isolation plus resume-entry editing and a one-page PDF preview; resume-entry revisions, approval, verification, and freezing; Handshake-channel graduation scoping in mapping, resolution, and eligibility; base resume storage and checksum stops; generated-resume layout and PDF conversion; sign-in detection; and a real-Chromium fixture upload of a rendered PDF. Agent-created Workday accounts are covered by `test:agent:workday-account` (fast: password policy, settings, verification-link acceptance), `test:agent:workday-account:local` (the owner-only accounts file, the hold gate, mailbox polling with a fake mailbox), `test:browser-worker:local` (pipeline account scenarios with an in-memory page), and `test:browser:workday-account` (real Chromium against routed synthetic Workday pages); the Gmail IMAP adapter itself is not exercised by any suite, since that needs the real mailbox. The Gmail outcome watcher is covered by `test:agent:mail` (fast: rules, matching, DM text, service renderers) and `test:agent:mail:local` (a fake IDLE session against a disposable workspace); the Gmail IDLE adapter itself is not exercised by any suite either. `test:browser:fixture` runs under tsx, whose keepNames output references an `__name` helper inside functions passed to `page.evaluate`; the fixture defines that helper in the page. Production builds do not emit it. The `github` gate covers deterministic extraction, disposable-SQLite incremental sync, and the seeded browser review flow. The `jobs` gate covers normalization contracts, disposable-SQLite ingestion and revision, and the seeded browser ingestion flow. The `discovery` gate covers batch parsing, bounded parsing of all five selected GitHub list formats and full-public-posting resolution, disposable-SQLite feedback and rate limits, and browser review controls. The `outcomes` gate covers transition guards, disposable-SQLite funnel and cost aggregation, and browser employer updates. The `matching` gate covers eligibility ordering contracts, disposable-SQLite match persistence with status transitions, and the seeded browser analysis flow.

Two explicit benchmarks never run implicitly:

- `pnpm verify:github:real -- --repo owner/repository`
- `pnpm verify:jobs:corpus`, which reads posting JSON files from the Git-ignored `data/job-postings/` directory. `pnpm corpus:build` populates that directory by resolving listing-repository links through the Greenhouse, Lever and Ashby public job-board APIs, because those repositories index postings without carrying their text (override with `INTERNSHIP_AGENT_POSTING_CORPUS`). It asserts structural reliability and reports what the classifier decided; it never treats model output as ground truth. Judging whether a hard/preferred split is correct remains a human review step.

## Public mirror

The repository stays private; a separate public repository mirrors it without candidate or employer details. `pnpm public:sync -- --public-dir <clone>` (`scripts/public-sync.mjs`) builds each update:

1. `git archive` of `--ref` (default `HEAD`) into a temporary folder, so only tracked files leave; `.env` files are never read.
2. The paths in `PRIVATE_ONLY_PATHS` (`HANDOFF.md`, `triage/`) are dropped, and `PUBLIC-README.md` replaces `README.md` (the private README stays private).
3. The deny-list `data/public-scrub.json` (Git-ignored by `data/*`; another file with `--scrub <file>`) is applied: `replace` rules (`find`, `replace`; literal, whole words unless `"word": false`, a space also matching a line break) swap real company names, employer tenant hosts and slugs, and other literals for neutral examples, longest first. 8-hex run or job ids become `<run id>` anywhere in a `.md` file and inside comments elsewhere. `pnpm-lock.yaml` is never rewritten.
4. A scan fails closed (exit 1, listing file, line, and rule, never the matched secret): any `replace` find still present in any case (unless `"scanCase": true`), any `forbid` pattern (personal identifiers kept only in the deny-list), any remaining run id, and secret shapes (API keys, GitHub, Slack, Google, and Discord tokens, private keys, assigned `*_API_KEY`/`*PASSWORD`/`*TOKEN`/`*SECRET` values) not listed in `allowSecrets` (fake test strings). Without a deny-list nothing is exported.
5. `--verify` runs `pnpm install --frozen-lockfile`, `pnpm typecheck`, and `pnpm test:harness` on a throwaway copy of the export.
6. The export is mirrored into the clone: files that disappeared are deleted, the clone's `.git` and ignored files are untouched, and a dirty clone is refused. The change is committed as the clone's configured author with the message `Sync from private <YYYY-MM-DD>` (no private commit messages or ids) and its diff stat printed. `--push` pushes; `--dry-run` does everything but write the clone and lists what would change; `--out <new dir>` also writes the scrubbed export to a new folder.

The deny-list holds the only copy of the real names, so it never enters either repository. Regressions: `testing-harness/harness/public-sync.test.mjs` (`pnpm test:harness`) with a fictional deny-list: replacement, run-id masking, fail-closed scans, and the clone sync.
